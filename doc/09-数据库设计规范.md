# 09 · 数据库设计规范

> 最后更新：2026-11-04  
> 适用：MySQL 8.x · `tender`

## 一、命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 表 | 小写、下划线、单数或领域名 | `notice`、`tender_project`、`crawler_task` |
| 字段 | 小写、下划线 | `notice_type_code`、`publish_time` |
| 主键 | `id` | `id bigint AUTO_INCREMENT` |
| 外键列 | `<表名>_id` / `<实体>_id` | `project_id`、`enterprise_id` |
| 布尔 | `is_` / `has_` / `enabled` / `deleted` | `has_attachment`、`enabled` |
| 时间 | `_time` / `_date` / `_deadline` | `publish_time`、`bid_deadline` |
| 金额 | `budget` / `price_ceiling` / `deposit_amount` / `win_amount` | 单位万元 |
| 索引 | `idx_<表缩写>_<字段>` | `idx_notice_type_publish` |
| 唯一键 | `uk_<表缩写>_<字段>` | `uk_source_url`、`uk_project_key` |
| 编码列 | `_code` 后缀 | `notice_type_code`、`province_code` |

## 二、主键与外键

- 业务表主键统一 `bigint` 自增；DO 使用 `@TableId` + `@KeySequence`。
- 单表 CRUD 使用 MyBatis-Plus；复杂查询用 `LambdaQueryWrapperX` / `@Select`。
- **业务表不建物理外键**，关联由应用层维护；仅 Quartz 表保留框架自带外键。
- 关联列必须建索引（如 `project_id`、`notice_id`、`enterprise_id`）。
- 多对多关系用中间表 + 唯一键（如 `notice_enterprise`）。

## 三、审计字段与逻辑删除

业务表统一继承 `BaseDO`，包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `creator` | varchar(64) | 创建者 |
| `create_time` | datetime | 创建时间，默认 `CURRENT_TIMESTAMP` |
| `updater` | varchar(64) | 更新者 |
| `update_time` | datetime | 更新时间，`ON UPDATE CURRENT_TIMESTAMP` |
| `deleted` | bit(1) | 逻辑删除，`b'0'` 未删 / `b'1'` 已删 |

约定：

- 查询默认过滤 `deleted = b'0'`（MyBatis-Plus 逻辑删除）。
- 物理删除只用于临时/日志表，业务表不物理删。
- 需要显式推进 `update_time` 时，在更新前 `setUpdateTime(LocalDateTime.now())`（框架只在为空时填充）。
- `tenant_id` 预留给多租户；当前 `tenant.enable=false`，业务写入默认 0。

## 四、数据类型

| 场景 | 类型 | 说明 |
|---|---|---|
| 主键/外键 | `bigint` | 自增 |
| 短文本 | `varchar(n)` | 按实际长度；不要一律 `varchar(255)` |
| 长文本/HTML | `longtext` / `text` | `notice.content` 用 `longtext` |
| 金额 | `decimal(18,2)` | 单位万元；禁止 `float` / `double` |
| 时间 | `datetime` | 精确到秒；日期用 `date` |
| 布尔 | `bit(1)` | `b'0'` / `b'1'` |
| 枚举/代码 | `varchar(32)` | 存代码，不存中文 |
| JSON | `json` | 配置、缺失字段、快照 |
| 哈希 | `varchar(64)` | SHA-256 十六进制 |
| 地区码 | `varchar(12)` | GB/T 2260 |

约定：

- 字符串默认 `''` 还是 `NULL`：**业务可空字段用 `NULL`**；状态/代码类用 `''` + 默认值。
- 金额统一万元，前端展示时再换算。
- 时间统一服务器时区 `Asia/Shanghai`。

## 五、索引规范

1. **唯一键优先**：业务唯一约束用 `uk_`，不要只靠应用层判重。
2. **高频查询列建索引**：`source_url`、`project_id`、`publish_time`、`notice_type_code`、`region_code`。
3. **复合索引顺序**：等值列在前，范围列在后；例如 `(notice_type_code, publish_time)`。
4. **避免过度索引**：写多读少的日志表只建必要索引。
5. **索引命名**：`idx_<表缩写>_<字段>`；唯一键 `uk_<表缩写>_<字段>`。
6. **大字段不建索引**：`content`、`text` 不建普通索引；全文检索用 ngram 全文索引（当前未启用）。

## 六、字符集与排序

- 库/表统一 `utf8mb4`。
- 新表跟随数据库默认 collation。当前 `tender` 库为 `utf8mb4_0900_ai_ci`。
- **不要在新表显式写 `utf8mb4_unicode_ci`**，否则与旧表比较可能报 `Illegal mix of collations`。
- 中文内容、emoji 均使用 `utf8mb4`。

## 七、迁移规范

| 场景 | 做法 |
|---|---|
| 新库初始化 | `tender.sql`（框架）→ `notice.sql`（业务最终结构 + 种子）；不需要执行 `refactor/P0-*` |
| 已存在库演进 | 在 `refactor/` 下新增 `P0-x__*.sql`，附 `*_rollback.sql`（历史迁移用） |
| 加列 | `ALTER TABLE ... ADD COLUMN`，用哨兵列保证幂等 |
| 删列 | 单独脚本 + 备份 + 回滚；P0-6 已在未上线阶段删除旧列 |
| 回填 | 单独脚本，按唯一键/`NOT EXISTS` 幂等 |
| 生产变更 | 必须先备份、先在测试库验证、避开高峰 |

约定：

- 所有 DDL 变更必须进入版本控制，不允许只在数据库手改。
- 每个迁移脚本头部写：目标库、前置、作用、幂等性、清理/校验脚本。
- 破坏性变更（删列/改类型）必须单独提交，并在文档中记录。

## 八、安全规范

- 数据库账号最小权限：应用账号只授予业务库 DML + 必要 DDL。
- 不在代码/脚本中硬编码生产密码；使用环境变量或配置中心。
- 敏感字段（手机号、联系人）按需脱敏；当前门户接口返回 `contactPhone`，后续按会员等级脱敏。
- 备份文件不入库、不进 Git；`backend/sql/mysql/refactor/backup/` 已忽略。
- 逻辑删除不等于脱敏；需要删除个人数据时按合规流程处理。
