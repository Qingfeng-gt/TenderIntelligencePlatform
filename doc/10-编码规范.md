# 10 · 编码规范

> 最后更新：2026-11-04

## 一、通用原则

1. **可读优先**：命名表达意图，避免缩写和魔法值。
2. **小步提交**：一个提交只做一件事，提交信息可追溯。
3. **不重复**：去重/入库/视图组装等公共逻辑上提，不在适配器/Controller 复制。
4. **显式失败**：业务错误抛 `ServiceException`，不要返回 `null` 让调用方猜。
5. **无副作用**：查询方法不写库；写方法明确事务边界。
6. **安全默认**：不记录密码/Token；不拼接 SQL；不信任前端参数。

## 二、Java 规范

### 2.1 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 类 | UpperCamelCase | `NoticeIngestionService` |
| 方法/变量 | lowerCamelCase | `getNoticeDetail`、`projectId` |
| 常量 | UPPER_SNAKE_CASE | `DEFAULT_LOT_NO` |
| 包 | 全小写 | `com.tenderintelligence.module.notice` |
| DO | `<Domain>DO` | `NoticePortalDO` |
| VO | `<Scene>ReqVO` / `<Scene>RespVO` | `NoticePageReqVO` |
| DTO | `<Domain>DTO` | `NoticeDTO` |
| Mapper | `<Domain>Mapper` | `NoticePortalMapper` |

### 2.2 分层

- Controller：参数校验 + 调 Service + `CommonResult.success`；不写业务。
- Service：业务规则、事务、跨表编排。
- Mapper：单表 CRUD / 条件查询；不写业务分支。
- DO/VO/DTO 转换用 `BeanUtils.toBean`；复杂映射显式写。
- 跨模块调用走 `api` 包接口，不直接注入对方 Mapper。

### 2.3 Lombok

- DO/VO/DTO 用 `@Data`；需要继承时用 `@EqualsAndHashCode(callSuper = true)`、`@ToString(callSuper = true)`。
- Service 用 `@Slf4j`、`@RequiredArgsConstructor` 或 `@Resource`（项目两种都有，保持同文件一致）。
- 不滥用 `@Builder`；需要时显式生成。

### 2.4 异常

- 业务错误：`throw exception(ErrorCodeConstants.XXX)`。
- 参数错误：`@Valid` + 校验注解，或 `throw exception(...)`。
- 不捕获异常后静默返回 `null`；至少记录日志并转换为业务错误。
- 不把堆栈/SQL 返回给前端。

### 2.5 事务

- 写多表用 `@Transactional(rollbackFor = Exception.class)`。
- 事务方法内不做远程调用/长耗时操作。
- 采集入库整体事务；适配器网络请求不在事务内。

### 2.6 日志

- 使用 `@Slf4j`，参数化日志：`log.info("...{}", id)`。
- 不打印密码、Token、完整手机号。
- 关键业务节点（采集开始/结束、状态流转、入库结果）打 INFO；异常打 ERROR + 堆栈。
- 不重复打印全局异常处理器已记录的异常。

### 2.7 并发与幂等

- 采集：单线程执行器 + RUNNING 检查。
- 需要分布式锁时用 Lock4j / Redisson，不手写 `synchronized` 跨实例。
- 写接口优先设计唯一键/幂等键，不依赖「先查后写」的单线程假设。

## 三、SQL / MyBatis 规范

- 表名/字段名小写下划线；SQL 关键字大写。
- 不使用 `SELECT *`；明确列名。
- 动态条件用 `LambdaQueryWrapperX` 的 `eqIfPresent` / `likeIfPresent`。
- 批量查询用 `selectListByIds` / `selectListByNoticeIds`，避免 N+1。
- 金额用 `BigDecimal`，不用 `double`。
- 逻辑删除由 MyBatis-Plus 处理，手写 SQL 记得加 `deleted = b'0'`。
- 原生 `@Select` 只用于聚合/统计；复杂 SQL 加注释说明口径。

## 四、TypeScript / Vue 规范

### 4.1 TypeScript

- 开启严格模式；避免 `any`，必要时用 `unknown` + 类型收窄。
- 接口类型放 `types.ts`，与后端 VO 对齐。
- 函数参数/返回值显式类型；公共工具函数写 JSDoc。
- 使用 `const` / `let`，不用 `var`。
- 异步用 `async/await`；错误用 `try/catch` 或 Promise `.catch`。

### 4.2 Vue

- 使用 `<script setup lang="ts">`。
- 组件名 PascalCase；页面放 `views`，复用组件放 `components`。
- Props 用 `defineProps<{...}>()`；事件用 `defineEmits`。
- 不在模板里写复杂表达式；抽成计算属性/方法。
- 列表渲染必须加稳定 `key`。
- 样式 scoped；全局样式放 `styles.css`。
- 不直接操作 DOM；需要时用 `ref` + 生命周期。

### 4.3 API 层

- 一个领域一个文件（`api/notice.ts`、`api/bid.ts`）。
- 请求函数返回 `Promise<T>`，拦截器统一解包 `data`。
- 不在组件里直接写 `axios`；统一走 API 层。
- 401 统一处理，不在每个页面重复写跳转。

### 4.4 样式

- 用户端使用 CSS 变量；管理端使用 Element Plus 主题变量。
- 移动端用 `rpx`，设计稿 750。
- 类名 kebab-case；避免 `!important`。
- 颜色对比度满足 WCAG AA。

## 五、Git 规范

### 5.1 分支

| 分支 | 用途 |
|---|---|
| `master` | 主分支，CI 触发 |
| `feat/<topic>` | 功能开发 |
| `fix/<topic>` | 缺陷修复 |
| `docs/<topic>` | 文档 |

### 5.2 提交信息

格式：

```text
<type>: <简短描述>

- 变更点 1
- 变更点 2
```

`type`：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`。

要求：

- 首行不超过 72 字符。
- 说明「为什么」而不只是「改了什么」。
- 不混入无关格式化。
- 不在提交信息中添加工具署名（项目约定）。

### 5.3 提交前检查

- [ ] 后端 `mvn -DskipTests compile` 通过。
- [ ] 前端 `pnpm build` / `pnpm ts:check` 通过。
- [ ] 新增/修改接口已更新文档。
- [ ] 新增/修改表已更新 ER 图与表说明。
- [ ] 无密码、Token、密钥、本地路径进入提交。

## 六、代码审查清单

- [ ] 命名清晰，职责单一。
- [ ] 无重复逻辑；公共逻辑已上提。
- [ ] 边界条件（null、空集合、分页越界）已处理。
- [ ] 异常/错误码正确，不吞异常。
- [ ] 事务边界正确。
- [ ] 查询无 N+1；必要索引已加。
- [ ] 前端类型与后端一致，无 `any`。
- [ ] 安全：鉴权、越权、SQL 注入、XSS、敏感日志。
- [ ] 文档与注释同步。
