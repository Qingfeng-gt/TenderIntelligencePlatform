# 12 · 部署与运维

> 最后更新：2026-11-04

## 一、环境矩阵

| 环境 | Profile | 数据库 | Redis | Quartz | 用途 |
|---|---|---|---|---|---|
| 本地 | `local` | 本机 MySQL `tender` | 本机 Redis | 关闭 | 日常开发 |
| 开发/测试 | `dev` | 测试库 | 测试 Redis | 启用 | 联调 |
| 生产 | `prod` | 生产 MySQL | 生产 Redis | 默认关闭；多实例按需 | 正式部署 |

> 生产配置模板：`backend/tender-server/src/main/resources/application-prod.yaml`。  
> 部署模板、Nginx、systemd、环境变量示例：`deploy/`。  
> 生产启动必须显式设置 `SPRING_PROFILES_ACTIVE=prod`，否则会按默认 `local` 启动。

## 三、数据库初始化

```bash
# 1. 框架基础（脚本会自动 CREATE DATABASE + USE tender）
mysql -uroot -p < backend/sql/mysql/tender.sql

# 2. 业务最终结构 + 基础/站点/菜单种子（业务表为空）
mysql -uroot -p < backend/sql/mysql/notice.sql

# 2.1 可选：20 条演示公告 + 四层关联，用于门户联调
mysql -uroot -p < backend/sql/mysql/demo-data.sql

# 3. 仅 dev/test 启用 Quartz 的环境
mysql -uroot -p < backend/sql/mysql/quartz.sql
```

> `notice.sql` 已是 **P0 终态结构**，不需要再执行 `refactor/P0-1 ~ P0-6`。  
> `refactor/` 仅用于已存在库的历史迁移；新库不要跑 `P0__run_all.sh`。
>
> `notice.sql` 对业务表是 **DROP + CREATE**：重复执行会清空业务数据并保留基础/站点/菜单种子；框架表（`system_*` / `infra_*` / `member_user`）不受影响。  
> 演示数据是独立可选的 `demo-data.sql`；正式采集前不需要执行它。

检查：

```sql
SELECT COUNT(*) FROM notice;              -- 新库为 0；导入 demo-data.sql 后为 20；采集后 > 0
SELECT COUNT(*) FROM project;             -- 同上
SELECT COUNT(*) FROM crawler_channel;     -- 35
SELECT COUNT(*) FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA='tender' AND TABLE_NAME='notice'
   AND COLUMN_NAME IN ('type','province','city','tender_person','agency','deadline','source');
-- 应为 0（notice.sql 直接创建终态结构，不含旧列）
```

> 备份默认写入 `backend/sql/mysql/refactor/backup/`（已 gitignore）。

## 四、后端启动

### 4.1 本地

```bash
cd backend
mvn -pl tender-server -am -DskipTests package
java -jar tender-server/target/tender-server.jar --spring.profiles.active=local
```

默认端口 `48080`。接口文档：`http://127.0.0.1:48080/doc.html`。

### 4.2 关键配置

`backend/tender-server/src/main/resources/application-local.yaml`：

| 配置 | 当前值 | 说明 |
|---|---|---|
| `server.port` | `48080` | 后端端口 |
| `spring.datasource.dynamic.datasource.master.url` | `jdbc:mysql://127.0.0.1:3306/tender` | 主库 |
| `username` / `password` | `root` / `123456` | 本地开发账号 |
| `spring.data.redis.host` | `127.0.0.1:6379` | Redis |
| `tender.crawler.schedule-enabled` | `true` | 定时采集开关 |
| `tender.crawler.schedule-cron` | `0 0 */2 * * ?` | 每 2 小时 |
| `tender.ai.api-key` | `${DEEPSEEK_API_KEY:}` | 环境变量注入，不写死 |
| `tender.security.permit-all-urls` | `/admin-api/notice/**` 等 | 匿名白名单 |

### 4.3 环境变量

| 变量 | 用途 | 是否必填 |
|---|---|---|
| `DEEPSEEK_API_KEY` | LLM 调用（规划中） | 使用 AI 功能时必填 |
| `SPRING_PROFILES_ACTIVE` | 指定 profile | 可选，默认 local |
| `MYSQL_PASSWORD` / 自定义 | 生产数据库密码 | 生产必填 |

> 生产环境不要把密码写在 `application.yaml`；使用环境变量/配置中心。

## 五、前端构建与部署

```bash
# 管理端
cd admin-web && pnpm install && pnpm build:prod   # dist-prod

# 用户端
cd user-web && pnpm install && pnpm build         # dist

# 移动端 H5
cd tender-app && pnpm install && pnpm build:h5    # dist/build/h5
```

### 5.1 Nginx 示例

```nginx
server {
    listen 80;
    server_name example.com;

    root /var/www/tender/user-web;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /admin-api/ {
        proxy_pass http://127.0.0.1:48080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /app-api/ {
        proxy_pass http://127.0.0.1:48080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

管理端可部署到独立域名或 `/admin` 子路径；`admin-web/.env.prod` 默认 `VITE_BASE_URL=''`，即使用同源 `/admin-api`，由 Nginx 反向代理。如果前后端分开域名部署，改成实际 API 地址。

## 六、生产环境（prod）

生产模板与清单已放在仓库：

| 文件 | 作用 |
|---|---|
| `backend/tender-server/src/main/resources/application-prod.yaml` | 生产 profile：环境变量占位、关闭 Swagger/Druid 控制台、收紧 Actuator |
| `deploy/env.prod.example` | 生产环境变量示例（复制到 `/etc/tender/tender.env`） |
| `deploy/systemd/tender-server.service` | systemd 服务单元 |
| `deploy/nginx/tender.conf` | 用户端/管理端 Nginx 反向代理与 HTTPS 模板 |
| `deploy/README.md` | 上线检查清单、构建/部署/升级/回滚步骤 |

生产启动：

```bash
SPRING_PROFILES_ACTIVE=prod \
DB_HOST=... DB_USERNAME=... DB_PASSWORD=... \
REDIS_HOST=... REDIS_PASSWORD=... \
java -jar tender-server/target/tender-server.jar
```

关键约定：

- 生产不要执行 `demo-data.sql`；
- 首次部署立即修改 `admin` 密码、停用/删除 `demo123`；
- `tender.captcha.enable=true`、`tender.security.mock-enable=false`；
- Actuator 只暴露 `health,info`；Swagger/Knife4j/Druid 控制台关闭；
- 采集 `CRAWLER_SCHEDULE_ENABLED` 在多实例时只在一台开启；
- 完整步骤见 [`deploy/README.md`](../deploy/README.md)。

## 八、备份与恢复

```bash
# 备份
mysqldump -uroot -p --single-transaction --routines --triggers tender \
  > tender_$(date +%Y%m%d_%H%M).sql

# 恢复
mysql -uroot -p tender < tender_20261104_1200.sql
```

| 对象 | 频率 | 保留 |
|---|---|---|
| MySQL `tender` | 每日 | 7~30 天 |
| Redis | 不需要（缓存/验证码/Token） | — |
| 附件 | 不落盘 | — |
| 配置 | Git | 永久 |

## 九、升级与回滚

### 8.1 升级

1. 备份数据库。
2. 拉取代码；新库执行 `tender.sql` + `notice.sql`；已存在库按需执行 `refactor/` 下的增量脚本。
3. 构建后端 + 前端。
4. 停旧进程 → 启新进程。
5. 冒烟：健康检查、公告列表、采集触发、登录。

### 8.2 回滚

| 场景 | 操作 |
|---|---|
| 代码回滚 | 切回上一个 tag/commit，重新构建 |
| 数据库结构回滚 | 执行对应 `*_rollback.sql`（P0-6 仅恢复结构，不恢复数据） |
| 数据恢复 | 用备份 restore |
| 采集异常 | 关闭 `tender.crawler.schedule-enabled`，手动重跑 |
