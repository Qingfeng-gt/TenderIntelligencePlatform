## 二、逐家拆解

### 2.1 千里马招标网（A）

#### 2.1.1 页面清单

来源：早期调研记录的千里马页面清单（已归档于 `doc/archive/`）。

| 分组 | 页面 | 入口 | 核心内容 |
|---|---|---|---|
| 信息浏览 | 首页 | `/` | 搜索框 + 行业分类导航 + 最新公告列表 + 推荐项目 |
| | 招标公告列表 | `/zbgg/` | 列表（标题/地区/发布日期/类型）+ 左侧筛选树（地区/行业/时间/金额）+ 分页 |
| | 中标公告列表 | `/zbgs/` | 同上，数据为中标结果 |
| | 变更公告列表 | `/bggg/` | 同上，数据为澄清/变更/延期 |
| | 采购意向列表 | `/cgyx/` | 正式招标前的预告信息 |
| | 拟建项目列表 | `/yjxm/` | 前期规划/可研/立项阶段项目 |
| | 招标详情页 | `/zbcontent-xxx.html` | 见 3.2 字段收敛格式 |
| 主体检索 | 企业搜索页 | `/company/` | 企业名称搜索 + 工商信息 + 历史中标记录 |
| | 采购单位搜索 | `/buyer/` | 按采购人搜索其历史招标项目 |
| 用户自有 | 订阅管理 | `/member/subscribe` | 新建/编辑订阅（关键词/地区/行业/金额区间/信息类型） |
| | 企业监控 | `/member/monitor/company` | 监控企业新中标/新投标动态实时提醒 |
| | 项目监控（项目专盯） | `/member/monitor/project` | 盯单个项目全阶段（公告→答疑→开标→中标） |
| | 我的收藏 | `/member/favorite` | 收藏的标讯列表 |
| | 数据导出 | `/member/export` | 按筛选条件导出 Excel |
| | 会员中心 | `/member/` | 账户信息、会员等级、订单 |
| 增值工具 | AI 标书工具 | `/ai/bid` | 上传招标文件 → AI 生成标书草稿（与 deepseek 合作） |
| | 竞争对手分析 | `/competitor/` | 输入竞对企业名 → 历史报价、中标业绩、技术关键词、价格策略 |

#### 2.1.2 关键机制

- **频道即类型**。千里马用**独立频道目录**承载不同类型的信息，而不是"一个列表 + 类型筛选"。这是它能把每个频道的列表页模板、筛选树都做成专用形态的原因（招标公告筛选"金额区间"，采购意向筛选"预计采购时间"）。代价是 URL 与类型强耦合。
- **监控一分为二**：企业监控（管主体）+ 项目专盯（管项目）。二者是两种不同的订阅对象，剑鱼把前者做深、把后者并入"在手项目"。
- **导出是显式付费动作**，独立成页并挂 `/member/` 下，与"收藏/浏览历史"同属付费墙内的功能群。
- **AI 标书是外挂**（与 deepseek 合作），不是自研模型——说明这条能力线的门槛在"拿到招标文件全文"而不是"生成能力"。

#### 2.1.3 数据模型要点（对本项目的对照价值）

| 频道 | URL | 语义 | 本项目 `notice.type` | 立达 `bid_info.bid_type` |
|---|---|---|---|---|
| 招标公告 | `/zbgg/` | 招标公告 | `tender` | 招标公告 |
| 中标公告 | `/zbgs/` | 中标结果 | `win` | 中标结果 |
| 变更公告 | `/bggg/` | 澄清/变更/延期 | `change` | 招标公告（`sub_type` = 变更） |
| 采购意向 | `/cgyx/` | 招标预告 | `explore` | 招标预告 / 采购信息 |
| 拟建项目 | `/yjxm/` | 前期规划/可研/立项 | **无对应值** | 拟建项目 |
| — | — | 商机预测 | 无 | 商机预测 |
| — | — | 拍卖信息 / 产权交易 | 无 | 拍卖信息 / 产权交易 |

**结论**：本项目 `NoticeTypeEnum` 的 4 个值（`tender`/`win`/`change`/`explore`）覆盖的是千里马频道里的前四个，即**"已发生的事实性公告"**。千里马与立达都额外挂了一整块"**未发生的前瞻性信息**"（拟建、预测），这块是独立的数据来源与独立的产品动作，不能靠 `type` 加枚举值解决。

### 2.2 剑鱼标讯（B）

#### 2.2.1 页面清单

来源：早期调研记录的剑鱼标讯页面清单（APP + Web，已归档于 `doc/archive/`）。

| 页面 | 核心内容 |
|---|---|
| 首页（推荐） | 搜索框 + 行业 Tab + 信息流（按订阅规则推送的标讯卡片） |
| 搜索结果页 | 关键词搜索 + 高级筛选（采购单位类型、有无附件、项目名称/标的物、发布时间） |
| 标讯详情页 | 公告全文 + 联系人电话 + 附件下载 + 收藏/订阅按钮 |
| 订阅页 | 普通订阅（2 个关键词免费）+ 超级订阅（多维度） |
| 企业资质库 | 上传企业资质证书 → 系统自动匹配要求对应资质的项目 |
| 监控中心 | 三合一：在手项目 + 重点业主 + 主要竞品 |
| 拟建项目 | 筹备期/审批期项目，提前介入 |
| 标讯导出 | 导出 Excel |
| 我的 | 收藏、浏览历史、推送设置、会员 |

#### 2.2.2 三个值得单独提炼的机制

**机制一：普通订阅 vs 超级订阅的免费/付费切分**

| 维度 | 普通订阅 | 超级订阅 |
|---|---|---|
| 关键词数量 | 2 个 | 不限 |
| 区域 | 单区/不限 | 多区域组合 |
| 信息类型 | 单一 | 多类型（招标/中标/变更/意向…） |
| 预算区间 | 无 | 有（金额上下限） |
| 资质匹配 | 无 | 有（对接企业资质库） |
| 计费位置 | 免费引流 | 付费墙 |

*启示：切分点选得极准——免费档给"能收到东西"的确定感，付费档全部押在**收窄噪声**上。用户付费不是为了更多数据，而是为了更少无关数据。*

**机制二：企业资质库 → 自动匹配**

用户上传自己的资质证书（如"建筑工程施工总承包二级"），系统反向匹配"资格要求中含该资质"的项目。这是**把"投标人资格要求"这个富文本字段结构化的产物**——没有结构化的资质要求字段，这个功能不成立。它是 B 相对 A/C 最锋利的一处差异化。

**机制三：监控中心三合一**

| 监控对象 | 用户意图 | 推送触发 | 对应千里马 | 对应立达 |
|---|---|---|---|---|
| 在手项目 | 我正在投的标有节点变动 | 项目阶段变更 | 项目专盯 | `project_progress` |
| 重点业主 | 我的甲方又发标了 | 该业主发布新公告 | 企业监控 | `monitor` + `monitor_dynamic` |
| 主要竞品 | 我的对手中标了 | 该企业成为中标人 | 企业监控 | `monitor` + `monitor_dynamic` |

三者共用一套监控底座（被监控主体 + 动态流），只是主体类型与触发条件不同。**这是"一个 `monitor` 表 + 一个 `dynamic` 表就能撑起整个监控中心"的证据**，立达的表设计印证了这一点。

#### 2.2.3 数据模型要点

- 订阅规则字段比千里马多出**金额区间**与**资质匹配开关**，说明 B 的订阅表需要 `min_budget`/`max_budget`/`qual_match` 三个字段。
- 监控与项目进度是两套独立关系：企业监控是"用户↔企业"，项目跟进是"用户↔公告/项目"。
- 详情页的四个动作——**公告全文、联系人电话、附件下载、收藏/订阅**——是标讯类产品的标准详情页四件套，缺一不可。

### 2.3 立达标讯（C）

数据来源：竞品数据库设计文档转写稿（15 张表 / 表清单汇总 / 字段来源追溯 / 数据字典总览），原 `.docx` 与转写稿均已归档于 `doc/archive/`。**截图未迁移，以下为按表反推的产品形态。**

#### 2.3.1 核心表逐表拆解

**① 标讯信息表 `bid_info`（25 字段，标讯模块主表）**

对应页面：招标公告、中标结果、合同临期等所有标讯类页面的列表与详情。

| 字段分组 | 字段 | 说明 |
|---|---|---|
| 标识 | `id`、`title`、`bid_type`、`sub_type` | 大类型 + 子类型双维度分类 |
| 地域 | `province`、`city` | 无区县，粒度到市 |
| 分类 | `industry`、`product_category` | 行业 + 产品分类，比本项目多一层"产品分类" |
| 金额 | `budget_amount`、`win_amount` | 单位**万元**，未公开为 `NULL` |
| 主体 | `tenderee_id`、`winner_id`、`agency_id` | **三根外键全部指向 `enterprise`**，是本表最重的设计决策 |
| 联系 | `contact_name`、`contact_phone` | 电话"脱敏存储" |
| 时间 | `doc_obtain_deadline`、`bid_deadline`、`sign_deadline`、`publish_time` | 三个截止时间：取标书 / 投标 / 报名 |
| 内容 | `content`（VIP 完整内容）、`has_attachment` | 正文本身就是付费墙 |
| 运营 | `status`、`view_count`、`created_at`、`updated_at` | |

- **`bid_type` 大类型枚举（全量 9 值）**：招标公告、中标结果、**合同临期**、招标预告、采购信息、**商机预测**、**拟建项目**、**拍卖信息**、**产权交易**。
- **`sub_type` 子类型枚举（全量 8 值）**：招标、资审、变更、流标废标、中标、开标、合同、评标候选人。

> 对照本项目 `notice.type` 的 4 个值：C 的大类型是 **9 值**，多出的 5 值是"合同临期 / 商机预测 / 拟建项目 / 拍卖信息 / 产权交易"。其中只有"合同临期"是**自己算出来的**（依赖 `contract` 表），其余 4 值都需要**独立数据源**。
> 更关键的差异：C 把"变更"放进了 `sub_type` 而非 `bid_type`。本项目的 `change` 是顶层类型。**若本项目未来引入子类型，`change` 需要重新归类**——这是数据模型规划期就要定的问题，见 [`08-数据模型-规划.md`](../数据/08-数据模型-规划.md)。

**② 企业表 `enterprise`（20 字段，企业模块主表）**

对应页面：招标单位列表/详情、中标单位列表、企业详情页。**一家企业同时可能是业主、中标单位、代理机构**。

| 字段分组 | 字段 | 说明 |
|---|---|---|
| 工商 | `name`、`logo`、`legal_person`、`registered_capital`、`established_date`、`email`、`address`、`province`、`city`、`industry` | 常规工商画像 |
| 分类 | `company_type` | 枚举：国有企业 / 政府及事业单位 / 通信运营商 / 军队 / 银行 / 证券 / 保险 / 医院 / 学校 |
| **角色标签** | `role_tags` | **逗号分隔：业主 / 中标单位 / 代理机构**——一个字段解决"一企多角色" |
| **招投标统计** | `bid_total_count`、`bid_total_amount`、`win_total_count`、`win_total_amount`、`contact_count` | 五枚冗余统计字段：招投标总数、采招总金额、中标总次数、中标总金额、联系人数量 |

- `role_tags` 是**冗余反范式**设计：不建关联表，用逗号串存角色，换来"按角色筛企业"时的零 JOIN。代价是无法按角色建索引。
- 五枚统计字段是**企业画像的最小可用集**：仅凭 `win_total_count` + `win_total_amount` 就能排出"该企业历史中标规模"，无需实时聚合。
- 注意 `enterprise_analysis` 表（见 ⑬）才是深度分析，`enterprise` 上的统计字段是**列表页/卡片上直接展示的浅层指标**。

**③ 合同表 `contract`（15 字段）——「合同临期」功能的唯一支撑**

对应页面：合同临期列表页。

| 字段 | 说明 |
|---|---|
| `bid_info_id` | FK，关联中标结果 |
| `title`、`contract_amount`、`contract_duration` | 合同标题 / 金额（万元） / 期限（天） |
| `start_date`、`end_date` | 合同起止 |
| `tenderee_id`、`winner_id`、`contact_phone`、`province`、`city` | 主体与地域（冗余，列表页直接渲染） |
| **`expire_status`** | **临期状态：1-一个月内，2-三个月内，3-半年内** |
| `has_attachment`、`publish_time`、时间戳 | |

> **这是立达最独特的字段，也是"合同临期"这个品类的全部秘密**：把 `end_date` 与当前日期做差，落到三个分档，用户就能收到"某单位的合同 X 个月后到期"——这是在**已公开的中标/合同公告里挖出的销售线索**，不需要任何额外数据源。`expire_status` 是**冗余的派生字段**（可由 `end_date` 算出），保留它是为了列表页能直接 `WHERE expire_status = 1` 命中索引，避免全表扫日期函数。
>
> 对本项目的直接含义：我们有中标公告（`win`），但**没有合同公告来源**，也没有 `contract` 表。功能可做，缺的是数据。

**④ 项目联系人表 `contact`（8 字段）【子表，关联企业】**

对应页面：项目联系人列表页。一对多：一企多人。

`id`、`enterprise_id`、`name`、`phone`、`contact_type`（招标联系人 / 中标联系人）、`source_bid_id`（来源标讯）、`status`、时间戳。

> 两个设计要点：**(a)** 电话字段注释明写"脱敏存储，VIP 可查看完整"——**付费点被写进了数据模型**；**(b)** `source_bid_id` 让每个联系人**可追溯到出处**，这既是数据质量手段（源站改稿可回溯），也是合规留痕。

**⑤ 用户订阅表 `subscription`（19 字段）**

对应页面：我的订阅列表页 + 新增订阅表单。

| 字段分组 | 字段 | 枚举/说明 |
|---|---|---|
| 名称 | `plan_name` | 方案名 |
| **关键词** | `keywords` | 逗号分隔，**最多 200 字** |
| **排除词** | `exclude_scope`、`exclude_keywords` | 范围：标题 / 全文；排除词逗号分隔 |
| **搜索方式/范围** | `search_mode`、`search_scope` | 方式：推荐 / 精准；范围：全文 / 标题 |
| **地区** | `provinces` | 逗号分隔，**空为不限** |

## 三、共性规律归纳

### 3.1 四层能力模型

四家竞品剥掉外壳后是**同一个四层结构**，层与层之间存在严格依赖：

| 层 | 能力 | 千里马 | 剑鱼 | 立达 | 标标达 | 依赖关系 |
|---|---|---|---|---|---|---|
| **L1 数据层** | 多源采集 / 去重 / 结构化 | 自有 + 采集 | 自有 + 采集 | `crawl_log` 表 | 全网同步 | 地基。**没有 L1，上面三层全是空壳** |
| **L2 检索层** | 关键词 + 多维筛选 + 保存订阅 | `/zbgg/` 筛选树、订阅管理 | 搜索 + 高级筛选、超级订阅 | `subscription`（19 字段） | 项目订阅 | 依赖 L1 的**字段完整度**——字段越全，筛选维度越多 |
| **L3 情报层** | 企业画像、竞品分析、监控预警、拟建预测 | `/company/`、`/buyer/`、`/competitor/`、企业/项目监控 | 企业资质库、监控中心三合一、拟建项目 | `enterprise` + `enterprise_analysis` + `monitor*` | 竞争分析、情报监控、市场分析 | 依赖 L2 的**结构化程度**——企业/资质/进度不结构化就做不了 |
| **L4 服务层** | AI 标书、一对一服务、数据导出 | AI 标书、数据导出、会员中心 | 标讯导出 | 浏览历史立即导出 | 专属项目经理、多账号 | 依赖 L3 的**用户信任**，是变现出口 |

**关键判断：本项目的当前能力全部落在 L1 与 L2 的下半层。** 后端勘察显示已实现的是采集（`crawler` + 两个 `SourceAdapter`）、公告存储与查询（`notice` + 3 个 `@PermitAll` 端点）、会员认证（`member`）、投标状态机（`bid_project`）。L3 情报层尚无一表一字段。这与竞品"十张表服务用户侧"的分布形成鲜明反差，也说明本项目下一步的增量空间在 L2 上半层（订阅）与 L3（监控）。

**层次不可跳级**：立达 `enterprise_analysis` 的 `analysis_type` 留白、本项目无 `enterprise` 表——都说明 L3 必须先有 L1 的企业结构化数据（本项目 `notice` 表里招标人/代理机构目前只是**两个字符串字段** `tender_person`/`agency`，不是实体），否则"企业画像"无从谈起。

| | 评标办法 | 无 | ❌ 未覆盖 |
| | 评分细则 | 无 | ❌ 未覆盖 |
| | 公告正文 | `content`（HTML，`#noticeArea` 或 `vF_deail_maincontent`） | ✅ 已覆盖 |
| | 附件列表 | 无（`notice` 无附件表，爬虫不下载附件） | ❌ 未覆盖 |
| | 原文链接 | `source_url`（唯一键 `uk_source_url`） | ✅ 已覆盖 |
| | 数据来源 | `source` | ✅ 已覆盖 |

**统计：已覆盖 8 项 / 部分覆盖 7 项 / 未覆盖 17 项。**

三条结论：

1. **已覆盖的 8 项全是"能从一个 HTML 页面正则抠出来"的字段**；未覆盖的 17 项大多是**需要跨区域取值的结构化字段**（保证金整区、采购人与代理的地址/联系人分列）或**需要下载附件才能得到的字段**（资格要求、评标办法、评分细则）。
2. **`tender_person` / `agency` / `contact` 是字符串而非外键**，与立达 `bid_info` 的三根企业外键（`tenderee_id`/`winner_id`/`agency_id`）是根本差异。这个差异**直接封死了 L3 情报层**——字符串无法稳定聚合出"某单位历史招标项目数"，也就做不出"企业画像"。**这是本项目通往 L3 的第一块必须搬开的石头**，见 [`08-数据模型-规划.md`](../数据/08-数据模型-规划.md)。
3. **`contact_phone` 明文存储**。竞品（立达 `contact.phone`、`bid_info.contact_phone`，均注明"脱敏存储 / VIP 可查看完整"）在此处是**有意为之的产品设计**。本项目当前既未脱敏、也未收费，属于**只有风险没有收益**的状态——个人电话属个人信息，公开发布不等于允许转售。**这一条应优先于任何功能开发处理。**

### 3.3 共性页面模式

四家的页面可以收敛为**四个模式**，本项目应直接复用这四套骨架，不要自创：

| 模式 | 结构 | 出现于 | 本项目现状 |
|---|---|---|---|
| **列表页** | 左侧筛选树（地区/行业/时间/金额）+ 右侧结果列表 + 底部分页 | 千里马全部 5 个列表频道、剑鱼搜索结果页、立达标讯全部列表 | ✅ 已有雏形：`NoticeListPage.vue` 为"顶部类型页签 + 三个下拉筛选"。**缺左侧筛选树与金额区间** |
| **详情页** | 信息栅格（8–12 格）+ 公告正文 + 附件区 + 「收藏 / 订阅」按钮组 | 千里马 `/zbcontent-*`、剑鱼标讯详情、立达详情 | ⚠️ `NoticeDetailPage.vue` 已有 8 格信息区 + `v-html` 正文 + 「发起投标」按钮。**缺附件区、缺收藏/订阅** |
| **订阅规则表单** | 关键词 + 排除词 + 搜索方式/范围 + 地区 + 信息类型 + 推送频率/时段 + 通知开关 | 千里马 `/member/subscribe`、剑鱼订阅页、立达新增订阅表单 | ❌ 无 |
| **监控列表 + 动态流** | 双 Tab（监控管理 / 监控动态）；管理页是主体列表 + 分组，动态页是时间倒序事件流 | 千里马企业监控/项目监控、剑鱼监控中心、立达监控两个 Tab | ❌ 无 |

**共同点中最值得注意的一条**：**收藏/订阅按钮出现在每一家的每一个详情页上**。它是"一次性浏览"转为"持续关系"的唯一入口，也是订阅/监控功能的漏斗起点。本项目详情页目前只有"发起投标"，**没有任何把匿名流量留下来的动作**——这是页面模式上最明显的缺口。

### 3.4 商业模式共性

| 维度 | 四家共同做法 | 证据 |
|---|---|---|
| **会员分级** | 至少三档，顶部留 to B 档 | 立达 `member_type`：0-普通 / 1-VIP / 2-SVIP / 3-企业会员；标标达"多账号使用"为会员权益；剑鱼普通订阅 vs 超级订阅 |
| **推送渠道** | 站内 + 邮件 + 微信/APP，多通道可开关 | 立达 `subscription` 三开关 `system_notify`/`wechat_notify`/`email_notify`；标标达"APP 推送和微信推送" |
| **推送节律** | 实时 + 定时两档，且**限定推送时段** | 立达 `push_frequency` 实时/定时 + `push_start_time` 06:00 / `push_end_time` 21:00 |
| **核心付费点 = 联系人电话** | 列表/详情展示脱敏，付费后可见完整 | 立达 `contact.phone` 注释"脱敏存储，VIP 可查看完整"、`bid_info.contact_phone`"脱敏存储"；标标达权益单里"各层级项目联系人电话""项目直接联系人""甲方重要负责人"占四项 |
| **正文也是付费点** | 详情正文对非会员截断 | 立达 `bid_info.content` 注释"公告正文（VIP 完整内容）" |
| **免费档给确定性** | 免费档保证"能收到东西"，付费档卖"收得更准" | 剑鱼普通订阅 2 个关键词免费，超级订阅卖区域/类型/预算/资质 |
| **人工服务兜底** | 高端档配专属服务 | 标标达"专属项目经理一对一金牌项目服务" |

**核心结论：这个行业的付费点从来不是"数据本身"，而是（a）联系方式、（b）降噪精度、（c）人工服务。** 数据是免费引流物。本项目若把商业模式建在"卖数据"上，方向就错了。

## 四、对本项目的启示

结论先行：**照搬 3 项、简化 5 项、暂不做 6 项、不做 3 项，另加 2 项竞品没做好但本项目必须做的事。**

| 能力 | 竞品做法 | 本项目取舍 | 理由 |
|---|---|---|---|
| **订阅推送** | 千里马 `/member/subscribe`；剑鱼普通（2 关键词免费）/超级（区域+关键词+类型+预算+资质）；立达 19 字段规则表含排除词、搜索方式/范围、推送时段、三通道开关 | **简化（本期做）** | 站内信与邮件排在前面：本平台已有 `system` 模块的站内信（`system_notify_message`）与会员体系，边际成本最低；微信订阅消息需要公众号资质与模板审批，**排到二期**。排除词、推送时段、搜索方式/范围、类型多选**照搬**立达（低成本、高感知）；**金额区间照搬**剑鱼（`notice.budget` 已有）；**资质匹配暂不做**（依赖 3.2 中未覆盖的"投标人资格要求"字段，无此字段则功能不成立） |
| **监控（企业监控）** | 千里马企业监控 + 项目专盯两条线；剑鱼三合一（在手项目/重点业主/主要竞品）；立达 `monitor` + `monitor_dynamic` + `monitor_group` | **简化（本期做企业监控，二期做项目监控）** | 企业监控只需"用户↔主体 + 动态流"两张表，且动态可由标讯增量自然产生，**不依赖新的数据源**；项目监控（"在手项目"）依赖 `project_progress` 式的阶段串联，而立达的 `project_progress` 靠 `related_bid_id` 把同一项目的多条公告挂成时间轴——本项目公告上下游关联尚未建立。**自定义监控分组照搬立达四类默认分组**（潜在客户/供应商/竞争对手/合作伙伴）；**分组表可先不建**，用 `monitor.group_name` 字符串承载，够用 |
| **企业画像** | 千里马 `/company/` `/buyer/` 企业搜索；立达 `enterprise` 20 字段 + `role_tags` 多角色 + 五枚招投标统计字段 + `enterprise_analysis`（JSON，VIP 专属） | **简化（本期建实体，不做画像页）** | **必须先做的是把 `notice.tender_person`/`agency` 从字符串升级为企业实体并建立外键**——这是所有 L3 能力的唯一前置条件，且**越晚做迁移成本越高**。画像页本身（图表、分析维度）本期不做：立达 `enterprise_analysis.analysis_type` 至今"待人工补充"，说明这块的产品形态连竞品都没定型，此时投入是赌 |
| **竞品分析** | 千里马 `/competitor/`（历史报价、中标业绩、技术关键词、价格策略）；标标达"预测竞争对手、可提前知道竞标对手" | **暂不做** | 拆成两半看：**"某企业历史中标记录"是既有数据的聚合，可做**（待企业实体化后用 `win` 类公告聚合）；但**"预测竞争对手"不可做**——它需要"哪些企业会来投这个标"的推断，竞品宣传里没有任何数据来源支撑。**预测性结论一旦错误，用户按它备标造成的损失会归到平台头上**，风险远大于收益 |
| **联系人电话** | 全部竞品脱敏展示、付费可见完整，是**行业第一大付费点** | **⚠️ 先合规，后产品（本期调整存储方式）** | 本项目 `notice.contact_phone` 目前**明文入库、匿名接口 `@PermitAll` 直接返回**（`/admin-api/notice/**` 全放行）——即**任何人无需登录即可批量拉取全国采购人手机号**。竞品是"脱敏展示 + 付费可见"，本项目是"全量明文 + 全量公开"，**只有风险没有收益**。处置顺序：**(1)** 接口层脱敏（中间四位打码）并收紧匿名面；**(2)** 采集层评估是否入库完整号码；**(3)** 商业模式验证后再谈"付费可见"，且需先解决个人信息处理的合法性基础。**此项优先级高于本期所有功能开发** |
| **附件下载** | 标标达宣称"每天 30 万+ 可下载招标文件附件"；剑鱼详情页含附件下载；立达有 `bid_attachment` 表 | **暂不做（分两步）** | **第一步只存源站链接，不下载、不转存**（`has_attachment` 标记 + 原文链接跳转）：成本近零、合规清晰、用户体验无损。**第二步（下载转存）持有明确反对理由**：招标文件通常有版权声明，转存后平台成为分发主体；源站普遍有防盗链；附件多为几十 MB 的 PDF/压缩包，存储与带宽成本与"免费用户"直接挂钩；且**下载后必然要做解析才能产生价值**（资格要求、评分细则），那是一次独立的解析能力建设。建议等"哪个字段真的影响用户决策"被验证后再投入 |
| **数据导出** | 千里马 `/member/export`；立达浏览历史页"立即导出"；剑鱼标讯导出 Excel | **简化（本期不做，二期做）** | 导出本身不难（框架已带 EasyExcel，`system`/`infra` 模块大量使用 `export-excel`），难的是**导出即批量落库**：一次导出 5 万条联系方式，等价于绕过所有页面级限制。且导出是竞品的**付费墙内功能**，本项目尚无付费体系，先做导出等于提前把最值钱的能力免费送出去。建议与会员分级一起上 |
| **AI 标书** | 千里马 `/ai/bid`，与 deepseek 合作，上传招标文件 → 生成标书草稿 | **不做** | 三重理由：**(a)** 依赖附件全文（本项目不下载附件），入口就没有；**(b)** 标书撰写是强专业、强责任场景，生成内容出错的责任无法界定；**(c)** 千里马是**找外部模型合作**而非自研，说明这是"有资源就能买"的能力而非差异化壁垒，本项目现阶段投入产出比不成立。若将来要做，形态应是"**招标文件要点提取**"（把 200 页 PDF 提炼成一页资格要求清单），而非生成标书 |
| **拟建 / 预测项目** | 千里马 `/yjxm/` 拟建项目；剑鱼拟建项目（筹备期/审批期）；标标达"提前 1-6 月独家预测项目" | **拆分处理：预告/意向照搬，拟建暂不做，预测不做** | **招标预告/采购意向（`explore`）照搬**——它是政府公开信息（采购意向公开是法定要求），本项目 `notice.type` 已有 `explore` 值，**只缺数据源**（见 [09-数据源清单.md](../数据/09-数据源清单.md)），接入即有产出。**拟建项目暂不做**——依赖发改委立项/可研批复类数据，来源分散、结构化程度低。**"提前 1-6 月独家预测"坚决不做**——"独家"意味着竞品自己造的，没有任何公开依据；向用户销售预测结论属于**实质性误导**，且一旦"预测"落空，平台承担的是商业损失责任 |
| **合同临期** | 立达独有：`contract` 表 + `expire_status`（1 个月 / 3 个月 / 半年三档） | **暂不做（记录为二期候选）** | 这是一个**设计上极巧**的功能——从公开的合同/中标公告中算出"谁的合同快到期了"，直接生成销售线索，**零额外数据源**。但本项目**没有合同类公告的来源**（`notice.type` 无对应值，采集站点未覆盖合同公告频道），且需要先有稳定的"中标 → 合同"关联。**建议作为二期第一个"从既有数据挖新功能"的实验项**，因为它不需要新数据、只需要新的加工方式，是最典型的 L3 能力样本 |
| **多账号** | 标标达会员权益"多账号使用"；立达 `member_type` 含"3-企业会员"档 | **不做** | 这是**计费方式**不是技术能力。本项目 `member_user` 是单体账号模型，多账号意味着引入"企业账户 ↔ 子账号"的数据权限体系——而本平台的 `tender-framework/tender-biz-data-permission` 模块尚在，但业务侧尚未使用数据权限。**在没有企业客户之前做多账号，是为不存在的需求付架构成本** |
| **会员分级**（补充） | 全行业三档起，顶部 to B 档 | **暂不做（但数据模型预留）** | 本期不建付费墙（无支付、无订单、无权益校验），但 `member_user` 应**预留会员等级与到期时间字段**，理由是事后加字段易、事后补"等级与内容的对应关系"难。立达把 `member_type` 放在 `user` 表而非独立权益表，说明**等级是用户属性而非独立实体**，本项目照此预留即可 |
| **列表页筛选树 + 金额区间**（补充） | 全部竞品列表页左侧均为多维筛选树 | **简化（本期做）** | 这是**投入产出比最高的一项**：数据已在库里（`province`/`city`/`industry`/`budget`/`publish_time`），缺的只是 UI。当前 `NoticeListPage.vue` 只有类型页签 + 三个下拉，**连库里已有字段都没暴露完**。补齐筛选树是纯前端工作量，且直接提升 L2 检索层可用性。**地区/行业/时间/金额四个维度照搬千里马** |
| **详情页收藏/订阅入口**（补充） | 每一家竞品的详情页都有 | **照搬（本期做）** | 当前 `NoticeDetailPage.vue` 只有"发起投标"按钮，**匿名流量看完即走，没有任何留存动作**。收藏（一张 `favorite` 表，5 字段）与"以此关键词建订阅"是把浏览转成关系的唯一入口，也是后续监控/推送功能的漏斗起点。**成本极低（立达 `favorite` 仅 5 字段），不做则后续所有 L3 功能都没有用户触达路径** |

### 取舍汇总

| 决定 | 项 | 合计 |
|---|---|---|
| **照搬** | 详情页收藏/订阅入口、订阅规则的排除词与推送时段、监控分组四类默认值 | 3 项 |
| **简化** | 订阅推送（先站内信/邮件，无微信、无资质匹配）、企业监控（先只监控企业）、企业画像（先建实体不做画像页）、列表页筛选树（补库内已有字段）、数据导出（与会员分级一起上） | 5 项 |
| **暂不做** | 竞品分析（不做预测部分）、附件下载（先只存链接）、合同临期（二期候选）、会员分级（预留字段）、拟建项目、附件解析 | 6 项 |
| **不做** | AI 标书、拟建/预测（预测部分）、多账号 | 3 项 |
| **⚠️ 必须优先处理** | `contact_phone` 明文 + 匿名接口全量暴露 | 1 项 |

### 三条最紧迫的行动

1. **收紧 `contact_phone` 的暴露面**（合规，优先级最高）。当前 `/admin-api/notice/**` 三个端点 `@PermitAll`、`contact_phone` 明文返回，等价于公开的联系方式数据库。
2. **把 `tender_person` / `agency` 升级为企业实体并建外键**。这是通往 L3 情报层的唯一路径，且是全库性的结构变更——**越晚迁移，既有数据越多，成本越高**。此项应在 [`08-数据模型-规划.md`](../数据/08-数据模型-规划.md) 定稿时一并决定。
3. **补齐列表页筛选树与详情页收藏入口**（纯前端 + 一张 5 字段表）。这是把已有数据变成可用产品的最短路径，也是竞品四家无一例外都做了的事。
