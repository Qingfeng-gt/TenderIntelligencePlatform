## 一、系统总览

### 1.1 物理部署视图

```
  admin-web (:80)                    user-web (:3001)
  Vue3+Vite+EP / pnpm                Vue3+Vite+EP / npm
     │ /admin-api 直连(代理已注释)      │ /admin-api（公告/统计，匿名）
     │                                │ /app-api（会员/投标，Bearer）
     │                                │ vite proxy → 127.0.0.1:48080
     └──────────────┬─────────────────┘
                    ▼  tender-server (:48080)  Spring Boot 3.5.15 / Java 17
     ┌──────────────────────────────────────────┐
     │ controller.admin → /admin-api             │
     │ controller.app   → /app-api               │
     │ service → dal(MyBatis-Plus)               │
     └──────┬──────────────────────────┬─────────┘
            ▼                          ▼
     MySQL(库 tender)             Redis(缓存/令牌/锁)
            ▲  写 notice / crawler_task
     ┌──────┴───────────────────────────────────┐
     │ 采集链路 tender-module-crawler             │
     │ 源站 → SourceAdapter → 解析 → upsert 去重   │
     └──────▲───────────────────────────────────┘
            │ HTTP（Cookie 预热 / Referer / UA / 限速）
     ccgp（中国政府采购网） · ztb_gz（贵州省招标投标公共服务平台）
```

- 两个前端**都指向 48080 同一个后端进程**，靠 URL 前缀分流：admin-web 走 `/admin-api`，user-web 走 `/app-api`（会员）与 `/admin-api`（公告）。
- admin-web 的 Vite 代理在 `admin-web/vite.config.ts` 中被**注释掉**，请求直连 `VITE_BASE_URL + VITE_API_URL`（`http://localhost:48080` + `/admin-api`），跨域由后端 `CorsFilter` 承担；user-web 则配了 `/admin-api` 与 `/app-api` 两条代理，`target: http://127.0.0.1:48080`。采集链路与 HTTP 请求链路则**完全解耦**：由 `ScheduledCrawlTask` 定时触发或管理端手动触发，直接由适配器写 `notice` 表。

### 1.2 分层视图

```
   外部调用方          user-web                 admin-web
   ====================▼=========================▼===========   HTTP / JSON
   ┌──────────────────────────────────────────────────────┐
   │ API 层（controller）                                  │
   │   **.controller.admin → /admin-api；.app → /app-api   │
   │   NoticePortal / Crawler / BidProject / BidPortal /   │
   │   MemberAuth 各 Controller                            │
   ├──────────────────────────────────────────────────────┤
   │ 鉴权横切：TokenAuthenticationFilter                    │
   │   /admin-api 要 ADMIN 令牌；/app-api 要 MEMBER 令牌      │
   ├──────────────────────────────────────────────────────┤
   │ Service 层（含 impl）：NoticeService / CrawlService /   │
   │   BidProjectService / MemberAuthService                │
   ├──────────────────────────────────────────────────────┤
   │ DAL 层（dal/dataobject + dal/mysql）：MyBatis-Plus      │
   │   BaseMapperX / LambdaQueryWrapperX                    │
   ├──────────────────────────────────────────────────────┤
   │ MySQL（库 tender） / Redis（缓存、令牌、分布式锁）         │
   └──────────────────────────────────────────────────────┘
```

分层**严格单向**：controller 不直接调 mapper，service 不感知 HTTP。唯一例外是采集链路——`SourceAdapter` 实现类内直接调用 `NoticePortalMapper` 完成 upsert，不经 service（见第五节）。

### 3.4 扩展指引

新增业务模块的标准动作是**三处挂载**：① 在 `backend/` 下创建 `tender-module-xxx`（`pom.xml` 的 `parent` 指向 `tender`）；② 在根 `backend/pom.xml` 的 `<modules>` 中加入该模块（位置需在 `tender-server` 之后，避免 Maven 反应堆顺序问题）；③ 在 `backend/tender-server/pom.xml` 的 `<dependencies>` 中加入对该模块的依赖——否则模块编译但不进容器，接口 404。另需确保类的包路径落在 `**.controller.admin.**` 或 `**.controller.app.**` 之下，否则拿不到 URL 前缀（见第四节）。

## 四、请求链路与鉴权

> 本章是全文档最容易踩坑的部分，务必通读。

### 4.1 前缀规则：由**包路径**决定，不是手写路径

Controller 上的 `@RequestMapping("/notice")` **不写** `/admin-api`。前缀由 `WebProperties` 按包名自动挂载（`tender-framework/tender-spring-boot-starter-web/**/config/WebProperties.java`）：

```java
private Api appApi   = new Api("/app-api",   "**.controller.app.**");
private Api adminApi = new Api("/admin-api", "**.controller.admin.**");
```

落地实现在 `TenderWebAutoConfiguration#webMvcRegistrations`：自定义 `RequestMappingHandlerMapping`，用 `AntPathMatcher(".")` 把 `Api.controller` 的 Ant 规则匹配到**类的包名**上，命中即设该前缀。

| 类所在包 | 实际 URL 前缀 | 示例 |
|---|---|---|
| `...controller.admin.**` | `/admin-api` | `NoticePortalController`（`controller.admin.notice`）→ `/admin-api/notice/**` |
| `...controller.app.**` | `/app-api` | `MemberAuthController`（`controller.app.auth`）→ `/app-api/member/auth/**` |
| 其它包 | **无前缀** | `tender-server` 的 `DefaultController` 需自行写全路径 |


**极易踩坑**：`NoticePortalController` 带的是「用户端门户」语义的注解（`@Tag("用户端 - 招投标公告")`），但它**放在 `controller.admin` 包**，真实地址是 `/admin-api/notice/**`，**不是** `/app-api/notice/**`。该前缀还直接决定令牌类型校验（4.3），写错前端就 403。另：`tender.web.admin-api.prefix` / `tender.web.app-api.prefix` **未在 yaml 覆盖**（`tender.web` 下只配了 `admin-ui.url`），取值全部来自 `WebProperties` 默认值。

### 4.2 放行机制：启动时扫注解 + yaml 清单

`TenderWebSecurityConfigurerAdapter#filterChain` 的授权规则构造顺序：

1. **静态资源**：`GET /*.html`、`/*.css`、`/*.js` → `permitAll()`。
2. **`@PermitAll` 扫描**：启动时遍历 `requestMappingHandlerMapping.getHandlerMethods()`，收集带**方法级**或**类级** `@PermitAll` 的 handler，**按 HTTP 方法**分桶（`Multimap<HttpMethod, String>`）后逐方法 `permitAll()`；若 handler 用 `@RequestMapping` 且未指定 `method`，视为 6 个方法全部放行。
3. **yaml 清单**：`tender.security.permit-all-urls`（`SecurityProperties#permitAllUrls`，默认空数组），`application.yaml` 中追加 `/admin-api/notice/**`。再加各 `AuthorizeRequestsCustomizer` 自定义规则。
4. **兜底**：`anyRequest().authenticated()`——**凡未显式放行的一律需要有效令牌**。其它固定项：`@EnableMethodSecurity(securedEnabled = true)`、CSRF 关闭、`SessionCreationPolicy.STATELESS`、CORS 开启。

#### 当前匿名可访接口清单（全量）

| 接口 | 方法 | 放行来源 |
|---|---|---|
| `/admin-api/notice/list`、`/notice/get?id=`、`/notice/stats` | GET | `@PermitAll` + yaml 清单 |
| `/admin-api/crawler/run?siteCode=` | POST | `@PermitAll` |
| `/admin-api/crawler/site/list`、`/task/page`、`/task/latest?siteCode=` | GET | `@PermitAll` |
| `/app-api/member/auth/login`、`/register`、`/logout` | POST | `@PermitAll` |

（另有框架自带的历史匿名端点，非本项目所写：`FileController`、`AuthController`、`CaptchaController`、`OAuth2OpenController`、`AppDictDataController`，以及 `tender-server` 的 `DefaultController`——它对已禁用模块返回 `NOT_IMPLEMENTED`，并含一个 `@PermitAll` 的调试端点 `/test`。）

> ⚠️ **安全债（上线前必须加固）**：`/admin-api/crawler/**` 这 4 个接口**当前完全匿名**——任何人都能触发全站采集、读取任务日志与站点配置。`CrawlerController` 类注释已明写「DEMO: PermitAll 匿名可调,正式版需管理员鉴权」。加固方式：去掉 `@PermitAll` 并加 `@PreAuthorize("@ss.hasPermission('crawler:...')")`。注意 `notice`/`crawler`/`bid`/`member` 四个模块目前**全模块无 `@PreAuthorize`**，仅 `system`/`infra` 使用。
>
> `/admin-api/notice/**` 的匿名放行是**有意设计**（未登录可浏览标讯），无需改动。另：`DefaultController` 的 `@PermitAll` 端点 `/test` 会回显 query/header/body，生产包应移除。

### 4.3 双令牌隔离：ADMIN 与 MEMBER 互不通用

令牌校验在 `TokenAuthenticationFilter`：

1. 取令牌：优先请求头 `tender.security.token-header`（默认 `Authorization`，`Bearer ` 前缀由 `SecurityFrameworkUtils#obtainAuthorization` 剥离），否则取参数 `tender.security.token-parameter`（默认 `token`）。
2. 调 `OAuth2TokenCommonApi#checkAccessToken` 校验有效性，拿到 `OAuth2AccessTokenCheckRespDTO`。
3. **关键一步**：由 `WebFrameworkUtils#getLoginUserType(request)` 依据 **URL 前缀**推导期望用户类型——`/admin-api/*` → `UserTypeEnum.ADMIN(2)`，`/app-api/*` → `UserTypeEnum.MEMBER(1)`；再与 `accessToken.getUserType()` 比对，**不匹配直接抛 `AccessDeniedException("错误的用户类型")`**（注意 WebSocket 的 `/ws/*` 不推导 userType，返回 `null` 时跳过比对，属框架刻意豁免）。

```
   admin-web  ──Bearer <ADMIN 令牌>──▶  /admin-api/**  ──▶ userType==2 ✔ 放行
   user-web   ──Bearer <ADMIN 令牌>──▶  /app-api/**    ──▶ userType==1? ✘ 403
   user-web   ──Bearer <MEMBER 令牌>─▶  /admin-api/**  ──▶ userType==2? ✘ 403
```

**设计原因**：两套用户体系（`system_users` 后台账号 / `member_user` 会员账号）共用同一套 OAuth2 令牌存储与校验接口，用户类型是唯一能区分「这张票是谁的」的维度。若不比对，会员令牌就能直接打管理后台接口。

**踩坑后果**：混用令牌时网关层不会提示「令牌无效」，而是 403 + `错误的用户类型`。排查时先看 `accessToken.userType` 与 URL 前缀，不必怀疑令牌是否过期——这一点在历史联调中反复出现。

### 4.4 开发者 mock 登录

`TokenAuthenticationFilter#mockLoginUser`：当 `checkAccessToken` 返回空（令牌不是真令牌）时，若 `tender.security.mock-enable = true` **且**令牌以 `SecurityProperties#mockSecret` 开头，则把**去掉前缀后的剩余部分直接当作 `userId`**，构造 `LoginUser` 塞进上下文。

- 开关：`tender.security.mock-enable`，**仅 `application-local.yaml` 为 `true`**，`SecurityProperties` 默认 `false`；密钥 `tender.security.mock-secret` 在 yaml 未覆盖，取默认值 `test`——因此 local 下 `Authorization: Bearer test1` 等价于「以用户 1 登录」。
- 用途：免登录调试后台接口、绕过验证码快速联调。

> ⚠️ **绝不能上生产**：开启后任何知道默认密钥的人只需伪造形如 `test<用户ID>` 的头即可获得任意用户身份。生产 profile 必须确保 `mock-enable` 为 `false`，并建议显式把 `mock-secret` 改为不可猜的值作双保险。

## 五、数据流

### 5.1 采集链路（源站 → notice）

```
 触发源 ① ScheduledCrawlTask @TenantIgnore：@Scheduled(cron="${tender.crawler.schedule-cron:0 0 */2 * * ?}")
         受 tender.crawler.schedule-enabled 控制　② POST /admin-api/crawler/run（手动）
   ▼  CrawlServiceImpl#run(siteCode)：failStaleTasks(4h) 回收超时任务 → 解析站点（单站点校验 enabled，
      否则取全部启用站点）→ 防重入（已有 RUNNING 则跳过）→ 每站点建 crawler_task(RUNNING)
      → 提交到【单线程守护线程池】crawler-run（串行化，避免打爆源站）
   ▼  SourceAdapter（构造注入 List<SourceAdapter>，按 code() 匹配）：ccgp → CcgpSourceAdapter +
      CcgpNoticeParser；ztb_gz → 贵州适配器 + 解析器。两段式：列表页/接口 → 详情页 → 解析字段；
      站点级 interval_ms 限速（默认 3000ms）
   ▼  解析 + 归一化 NoticeRegionExtractor（两解析器共用）：extractRegion → [province, city]（词典命中才
      采纳）；detectIndustry → 15 类关键词首命中；均兜底 "其他"（规则推导，非源站字段）
   ▼  upsert()（两适配器内各写一份，未上提到服务层）：NoticePortalMapper#selectBySourceUrl（DB 唯一键
      uk_source_url）→ 不存在 INSERT（newInsert++）／已存在则比对 title/deadline/budget/content/
      province/city/industry，有变 updateById（updated++）
   ├─▶ notice 表（正文片段 + 结构化字段；原始页面 HTML 不入库）；└─▶ crawler_task 表：SUCCESS/FAILED，CrawlStats 记
       listFetched / listParsed / detailFetched / detailFailed / newInsert / updated（errorMsg 截断 500 字）
```

去重键是 `notice.source_url`（DDL 中 `UNIQUE KEY uk_source_url`，允许 `NULL`）。接入新站点 = 实现 `SourceAdapter` 接口（`code()` + `crawl(site, stats)`）+ 在 `crawler_site` 加一行配置，**无需改 YAML**。详见 [`06-数据采集设计.md`](06-数据采集设计.md) 与 [`09-数据源清单.md`](../数据/09-数据源清单.md)。

> 当前状态：`ztb_gz` 源站 `search` 列表接口 2026-09-08 实测返回 `totalNum=0`（列表数据下线），`GetDetail` 仍可用；因此截至撰写日实际产出数据的只有 `ccgp`。

### 5.2 用户链路（未登录浏览 → 登录投标）

```
 未登录：
   user-web 首页/列表 ──GET /admin-api/notice/{list,stats,get}（匿名，不带 Authorization）
   ▼  NoticePortalController → NoticeServiceImpl → NoticePortalMapper → notice 表

 已登录（会员）：
   user-web 登录页（账号密码 + 滑块验证码）
     POST /admin-api/system/captcha/get | /check（裸 axios，AJAX-Captcha 协议）
     POST /app-api/member/auth/login（@PermitAll，返回 accessToken）
   ▼  MemberAuthServiceImpl → OAuth2TokenService.createAccessToken(..., UserTypeEnum.MEMBER, ...)
      令牌写入 localStorage['tender_member_token']
   「发起投标」/「我的投标」 ──Bearer <MEMBER 令牌>──▶ /app-api/bid-project/{create,list,status}
   ▼  BidPortalController → BidProjectServiceImpl ──读──▶ notice 表（载入源公告）
                                                  ──写──▶ bid_project 表
```

**投标状态机**（`BidProjectStatusEnum`，`allowed(from, to)` 为守卫）：

```
   SUBMITTED ──┬──▶ OTB ──┬──▶ WON       （终态）
   已提交       │  已开标   ├──▶ LOST      （终态）
               │          └──▶ ABANDONED （终态）
               └──▶ ABANDONED（终态）
```

`createBidProject` 先查 `selectActiveByUserAndNotice`（`status IN SUBMITTED/OTB`），同一会员对同一公告**在途投标只允许一条**，重复抛 `BID_PROJECT_ALREADY_EXISTS`；非法迁移抛 `BID_PROJECT_STATUS_ILLEGAL`。

### 5.3 时间字段契约（历史踩坑点）

后端 Jackson 全局配置 `spring.jackson.serialization.write-dates-as-timestamps: true`，后果是 **`LocalDateTime` 字段序列化为 epoch 毫秒（数字），不是 ISO 字符串**。前端直接渲染会显示成裸数字或被判为非法时间。

- user-web 必须用 `user-web/src/utils/format.ts` 的 `formatDateTime`（→ `YYYY-MM-DD HH:mm`）或 `formatDateTimeShort`（→ `MM-DD HH:mm`）；两者兼容 epoch 毫秒 **和** ISO 字符串，空值统一渲染 `'—'`。该文件头部注释已显式记录此契约。admin-web 侧对应封装是 `admin-web/src/utils/formatTime.ts`（基于 dayjs），**与 user-web 的实现相互独立**。
- 反向（前端传后端）时，`publishTimeGreaterThan` 等参数需传 `yyyy-MM-dd HH:mm:ss` 字符串，user-web 由 `api/notice.ts` 内部的 `toTimeParam` 完成 `''/'today'/'week'/'month'` → 字符串的转换。

历史上首页「一直加载」的故障即由此而来，改动时间字段渲染时务必回归。

### 6.1 为什么 Quartz「仅 dev 启用」

**一句话：这是脚手架基线带来的默认值，不是本项目的架构选择**，本项目自己的定时业务（采集）根本不走 Quartz。

- **来源**：`application-local.yaml` 的 `spring.autoconfigure.exclude: QuartzAutoConfiguration` 与 `application-dev.yaml` 的整段 `spring.quartz.*` 都出自代码基线（开源快速开发脚手架），从 `d7e82fc`「多租户模板基线」起就是这样，至今未有针对本项目的调整。
- **local 排除的理由**：本地开发不需要 Quartz —— 排除自动配置可省掉 11 张 `QRTZ_*` 表的依赖与启动开销，少一个建库前置步骤（这正是 `quartz.sql` 被标注为「仅启用 Quartz 的环境需要」的原因）。
- **dev 启用的理由**：dev 用于联调，需要真实跑通 `infra_job` 里的任务（默认启用的是 `tokenCleanJob`），所以按脚手架默认以 `job-store-type: jdbc` + `isClustered: true` 启用，并要求先导入 `quartz.sql`。
- **对采集没有影响**：`ScheduledCrawlTask` 是 Spring 原生 `@Scheduled`，与 Quartz 开关无关，两种 profile 下行为一致。

**那项目里到底有没有真的跑在 Quartz 上的任务？有，但全是框架自带的运维清理任务，没有一个是业务功能** —— `infra_job` 种子共 4 条（`backend/sql/mysql/tender.sql`），注意**其中 3 条种子里就是「暂停」状态**（`status=2`，见字典 `infra_job_status`）：

| id | 任务 | handler（=Spring bean 名） | 默认状态 | cron |
|---|---|---|---|---|
| 13001 | 登录令牌清理 Job | `tokenCleanJob`（`module-system/job/token/TokenCleanJob.java`） | **正常**（`status=1`） | `0 0 2 * * ?` |
| 25 | 访问日志清理 Job | `accessLogCleanJob` | 暂停（`status=2`） | `0 0 0 * * ?` |
| 26 | 错误日志清理 Job | `errorLogCleanJob` | 暂停（`status=2`） | `0 0 0 * * ?` |
| 27 | 任务日志清理 Job | `jobLogCleanJob` | 暂停（`status=2`） | `0 0 0 * * ?` |

即 **dev 下真正会被 Quartz 触发执行的只有 `tokenCleanJob`**（每天 02:00）；另外三个要在管理端「定时任务」页面手动启用才会跑。所以「项目用不到 Quartz」这个印象，对**业务**成立，对**工程底座**不成立 —— 上生产时仍需为这 4 条任务决定新 profile 的 Quartz 开还是关。

> 附带一个容易被忽略的耦合：**采集的 `@Scheduled` 能生效，恰恰依赖这个 job starter**。`@EnableScheduling` 声明在 `TenderQuartzAutoConfiguration`（该类列在 `tender-spring-boot-starter-job` 的 `AutoConfiguration.imports` 中，**无条件加载**）。`local` 排除的是 Spring Boot 自带的 `org.springframework.boot.autoconfigure.quartz.QuartzAutoConfiguration`，其结果只是容器里**没有 `Scheduler` bean**：该配置类以 `Optional<Scheduler>` 注入，取不到便打印「[定时任务 - 已禁用]」并降级为 `SchedulerManager(null)`，**`@EnableScheduling` 照常生效**。换言之：若哪天把这个 starter 整个移除，采集定时会一起失效。

> ⚠️ **上生产要留意**：当前仓库**只有 `local` 与 `dev` 两个 profile，没有 `prod`**。`dev` 的 Redis 指向远端、`captcha.enable` 默认开启、`mock-enable` 默认关闭，作为生产配置并不合适；若新增 `prod` profile，**Quartz 这一段必须显式决策** ——
> - 要跑 `infra_job` 的任务 → 照抄 dev 的 `spring.quartz.*` 并导入 `quartz.sql`；
> - 不打算启用 → 照抄 local 的 `spring.autoconfigure.exclude` 排除掉，此时管理端「定时任务」页面上的任务**不会真的执行**。
>
> 无论选哪种，**采集定时都不受影响**（不依赖 Quartz）。

### 7.2 裁剪后存活的管理端菜单树

菜单**由服务端下发**（`admin-web/src/store/modules/permission.ts` 读 `CACHE_KEY.ROLE_ROUTERS` 后 `generateRoute`），权威定义在种子 SQL：`backend/sql/mysql/tender.sql`（系统/基础设施）+ `backend/sql/mysql/notice.sql`（业务顶级菜单）。

```
│       ├─ 操作日志 /system/log/operate-log  SystemOperateLog  id 21
│       └─ 登录日志 /system/log/login-log    SystemLoginLog    id 22
├─ 基础设施 /infra                    （id 2，ep:monitor）
│   └─ 定时任务 /infra/job    InfraJob          id 14
└─ 数据采集中心 /crawler              （id 12800，ep:data-analysis，顶级）
              component crawler/index，component_name CrawlerCenter
```

- 「数据采集中心」由 `backend/sql/mysql/notice.sql` 以 `ON DUPLICATE KEY UPDATE` 幂等插入；注释已说明**超管隐式拥有全部菜单，故无需 `system_role_menu` 行**。「我的站内信」不在左侧菜单树中，是用户中心里的入口：`/user/notify-message` → `admin-web/src/views/system/notify/my/index.vue`。

### 7.3 历史遗留提醒

- **`system_users` 表仍保留 `dept_id` / `post_ids` 列**（`tender.sql` 第 963–964 行，另有 `idx_dept_id` 索引），`system_role` 保留 `data_scope_dept_ids`；本地数据中 `admin` 用户 `dept_id=103`、`post_ids='[1,2]'`。部门/岗位的表与代码已删，这些列是**纯历史遗留**，值可能为空或脏数据，**不要依赖、也不要据此判断业务逻辑**。前端 `UserVO` 仍带 `deptId` / `deptName` / `postIds` 字段，仅为兼容接口结构。
- 绝大多数业务表仍带 `tenant_id` 列（`notice`、`crawler_site`、`crawler_task`、`bid_project`、`member_user`、`system_*` 等），种子数据统一写 `0`；`system_users` 中 `admin` 行为 `1`。虽然 `tender.tenant.enable=false` 使其不参与 SQL，但**保留该列可避免未来回退多租户时的迁移成本**，也不影响当前查询。
