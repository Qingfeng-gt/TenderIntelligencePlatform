## 一、采集总览

**设计目标**：把政府公开的招投标公告，从**多源、异构**的站点稳定地采集、归一、去重后落入 `notice` 表，供用户端检索。**多源** = 静态 HTML 列表页（中国政府采购网）与 JSON 接口（贵州省招标投标公共服务平台）并存；**异构** = 字段命名、页面结构、日期格式、金额单位、地区编码全不一样；**稳定** = 源站随时改版、限流、下线，采集不能崩、不能写脏数据。

**数据流**：

```
   源站（HTML 列表/详情页 │ JSON 列表/详情接口）
      │ HttpClient + CookieManager（UA / Referer / X-Requested-With 等反爬头）
      ▼
   SourceAdapter（每站点一个 @Component 实现）
     ├─ 第 1 段  列表页 → 候选详情 URL 集合          → listFetched++ / listParsed++
     └─ 第 2 段  详情页 → 原始 HTML / JSON           → detailFetched++ / detailFailed++
                 （仅内存中转：解析完只留正文片段 + 结构化字段，原始页面不落库）
      ▼
   字段解析  XxxNoticeParser.parse(...) → NoticePortalDO
     （CCGP：HTML 正则锚点；ztb_gz：JSON 字段 + 正文纯文本锚点正则）
      ▼
   归一化  NoticeRegionExtractor（province / city 省市词表；industry 15 行关键词词典）
      ▼
   去重 upsert（按 notice.source_url）
     ├─ 不存在      → insert  newInsert++
     └─ 存在且有变  → update  updated++
      ▼
   notice 表（uk_source_url 唯一键）

   旁挂：crawler_task 任务日志（由 CrawlServiceImpl 统一写，适配器不写；
        状态 RUNNING → SUCCESS/FAILED，6 个计数器 + error_msg）
```

**核心设计原则**：

| 原则 | 含义 | 落地方式 |
|---|---|---|
| **适配器模式** | 站点差异收敛在适配器内，主干（调度、任务日志、并发控制、统计）不变 | `SourceAdapter` 接口 + `@Component` 自动发现，主干只面向接口编程 |
| **两段式采集** | 列表页只产出「候选详情 URL」，详情页只产出「字段」 | 两适配器都是「先翻完列表收集 URL，再统一抓详情」 |
| **采集即加工** | 抓回的详情页**不整页留存**，入库前先截正文、抽字段 | 解析器 `extractContent()` 只保留正文区段，页面骨架/样式/推荐位在解析阶段丢弃；`notice` 表无「原始 HTML」列 |
| **串行 + 频控** | 一次只跑一个任务，同站详情间强制休眠，不打爆源站 | 单线程守护线程池 + `interval_ms`（默认 3000ms） |
| **可配置化** | 站点/频道配置在 DB，不在 YAML | `crawler_site` 表 + `channels` / `config` 两列 JSON；**新增源站不改配置文件、不重新打包** |

## 二、可扩展点：SourceAdapter 契约

### 2.1 接口全文

`service/adapter/SourceAdapter.java` —— 整个采集体系只有两个方法：

```java
/**
 * 数据源适配器接口: 两段式采集(列表页 → 详情页) → 解析字段 → 入库
 *
 * 新源站实现本接口, 并在 crawler_site 表新增一行配置即可扩展
 */
public interface SourceAdapter {

    /** 站点标识(与 crawler_site.code 对应) */
    String code();

    /** 执行一次采集(列表→详情→解析→入库, 统计数据写入 stats) */
    void crawl(CrawlerSiteDO site, CrawlStats stats) throws Exception;
}
```

**契约要点**：

- `code()` 必须与 `crawler_site.code` 逐字一致，这是适配器与站点配置的唯一关联键。适配器**不需要知道 URL** —— `baseUrl` 从 `site.getConfig()` 里读。
- `crawl()` 入参 `site` 是完整 `CrawlerSiteDO`（含 `name`，用作 `notice.source`；含 `channels`、`intervalMs`、`config`）。**两个 JSON 由适配器自己解析**，主干不掺和 —— 这是「同 schema 承载不同站点语义」的关键。
- `stats` 是出参：适配器只往计数器上累加，**不负责落库任务日志**（那由 `CrawlServiceImpl.runSite` 收尾时统一完成）。
- 抛异常 = 整站点失败，主干捕获后写 `FAILED` 并把 `error_msg` 截断到 500 字符。**单条详情的失败必须由适配器自行吞掉并 `detailFailed++`**，不能让一条坏数据毁掉整轮采集。

### 2.2 接入一个新源站的完整步骤

这是本设计**最重要**的特性 —— 新增源站的边际成本是「一个类 + 一行 SQL」：

1. **实现 `SourceAdapter`**：`code()` 返回站点标识（如 `"ggzy"`），`crawl()` 内完成「列表 → 详情 → 解析 → upsert」。类加 `@Component`。
2. **在 `crawler_site` 插入一行**：配好 `name`、`code`、`enabled`、`interval_ms`、`channels` JSON、`config` JSON。
3. **字段结构差异大时写配套的 `XxxNoticeParser`**：静态 `parse(...)` 输出 `NoticePortalDO`；地区/行业逻辑直接复用 `NoticeRegionExtractor`，不重复实现。
4. **无需改动**：`CrawlService` / `CrawlServiceImpl` / `ScheduledCrawlTask` / `CrawlerController` / 管理端页面**一律不动**。

第 4 条是抽象的收益所在：调度、并发护栏、任务日志、统计口径、管理端展示全部对适配器无感。

### 2.3 适配器发现机制

实现类标 `@Component`，Spring 启动时全部注册为 Bean；`CrawlServiceImpl` 经**构造注入**拿到全集，运行时按 `code()` 线性匹配：

```java
private final List<SourceAdapter> adapters;          // Spring 自动注入全部实现
public CrawlServiceImpl(List<SourceAdapter> adapters) { this.adapters = adapters; }

private SourceAdapter findAdapter(String code) {
    return adapters.stream().filter(adapter -> adapter.code().equals(code)).findFirst().orElse(null);
}
```

匹配不到**不抛异常**，而是把任务置 `FAILED`、`errorMsg = "无对应适配器: " + site.getCode()` —— 保证「先加 DB 配置、后发版加适配器」（或反之）都不会让进程异常。

## 三、站点配置模型（`crawler_site`）

### 3.1 表结构

| 列 | 类型 | 含义 |
|---|---|---|
| `id` | bigint PK | 站点编号，自增从 100 起 |
| `name` | varchar(64) | 站点名称。采集时作为 `notice.source`（来源网站名）写入 |
| `code` | varchar(32) | **站点标识**，与 `SourceAdapter.code()` 一一对应；唯一键 `uk_code` |
| `enabled` | bit(1) | 是否启用，默认 `b'1'`。`run(null)` 时过滤掉 `false` 的站点；单独指定 `siteCode` 但停用时抛 `CRAWLER_SITE_DISABLED` |
| `channels` | varchar(1024) | 频道配置 JSON，默认 `''`，见 3.2 |
| `interval_ms` | bigint | 详情页请求间隔（ms），默认 3000；适配器读到 `null` 亦回落 3000 |
| `config` | varchar(2048) | 抓取配置 JSON（UA / 首访 URL 等），默认 `''`，见 3.3 |

另含 `creator` / `create_time` / `updater` / `update_time` / `deleted` / `tenant_id` 等 `BaseDO` 通用审计与逻辑删除列。

### 3.2 `channels` JSON 结构

数组，元素 `{path, name, type, pageCount}`。**同一 schema 在两个适配器里承载不同语义**，这正是适配器模式的价值：

| 字段 | CCGP 语义 | ztb_gz 语义 |
|---|---|---|
| `path` | 列表页**路径前缀**（如 `/cggg/dfgg/gkzb/`） | search 接口的 **`noticeType` 类别编码**（如 `A01`） |
| `name` | 频道中文名 | 频道中文名（用于日志输出） |
| `type` | 直接落入 `notice.type`；缺省 `"tender"` | 同左，但仅作类型判定的**第三级兜底** |
| `pageCount` | 翻页数，默认 1 | 同左 |

解析实现的两处差异（源码事实）：`CcgpSourceAdapter.parseChannels` 用 `node.get("path").asText()`（**无 null 保护**，`path` 缺失会 NPE 并被外层 catch 吞掉），全数组解析为空时兜底频道 `/cggg/dfgg/gkzb/`（tender，1 页）；`GuizhouZtbSourceAdapter.parseChannels` 用 `node.has("path") ? node.get("path").asText() : "all"`（带保护），`name` 缺省取 `noticeType`，兜底频道 `noticeType="all"` / `name="全部公告"` / `type="tender"` / `pageCount=1`。

**当前 `ccgp` 的 4 个频道**（`pageCount` 于 2026-09-11 由 1 调为 5，理由见下方说明）：

```json
[{"path":"/cggg/dfgg/gkzb/","name":"地方-公开招标","type":"tender","pageCount":5},{"path":"/cggg/dfgg/zbgg/","name":"地方-中标公告","type":"win","pageCount":5},{"path":"/cggg/dfgg/gzgg/","name":"地方-更正公告","type":"change","pageCount":5},{"path":"/cggg/dfgg/xjgg/","name":"地方-询价公告","type":"explore","pageCount":5}]
```

**为什么是 5 页（2026-09-11 实测依据）**：

| 实测项 | 结果 |
|---|---|
| CCGP 列表翻页 URL | 第 1 页 `{path}`，第 N 页 `{path}index_{N-1}.htm`（`CcgpSourceAdapter` 内 `page <= channel.pageCount` 循环） |
| 单页条数 | 20 条（`LIST_ITEM` 正则命中数） |
| **单日发布量** | gkzb 频道翻到**第 14 页**仍在当天（2026-09-11）内 —— 即该频道**单日约 300 条** |
| 5 页覆盖 | 约 8 小时积压量，对应 2 小时的采集间隔 = **4 倍安全余量** |
| 单轮成本 | 4 频道 × 5 页 = 400 条候选；详情限速 3s ⇒ 约 20 分钟（≈3 请求/分钟，对源站足够礼貌） |

> 结论：`pageCount=1`（每轮仅 80 条候选）时，实际只能覆盖当天发布量的零头，属**大面积漏标**。改用 5 页后单轮候选 80 → 400，实测首轮新增入库 380 条（此前从未采到）。分页 URL 与正则在改动前已用 `curl` 逐页验证。

**当前 `ztb_gz` 的 3 个频道**：

```json
[{"path":"A01","name":"招标公告","type":"tender","pageCount":1},{"path":"A02","name":"变更公告","type":"change","pageCount":1},{"path":"A04","name":"中标结果公示","type":"win","pageCount":1}]
```

### 3.3 `config` JSON 结构

| 键 | 作用 | 缺省值 |
|---|---|---|
| `baseUrl` | 站点根地址。列表 URL、详情 URL、相对链接拼装全部基于它 | ccgp `http://www.ccgp.gov.cn`；ztb_gz `http://ztb.guizhou.gov.cn` |
| `initialUrl` | **会话预热 URL**。采集前先 GET 一次：取服务端 Cookie，并把 UA 交给 `CookieManager` 会话 | `baseUrl + "/"` |
| `userAgent` | 请求头 `User-Agent`，默认 Chrome 120 桌面 UA（两适配器各有一份 `DEFAULT_UA` 常量） | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36` |
| `xhrReferer` | **仅 ztb_gz 使用**。发给 `search` 与 `GetDetail` 两个 XHR 接口的 `Referer`，伪装成从交易公告页发起的前端调用 | `baseUrl + "/trade/?category=affiche"` |

`notice.sql` 中两行种子配置（`id=1` ccgp、`id=2` ztb_gz，均 `interval_ms = 3000`、`tenant_id = 0`）的 JSON **原文**：

```json
// ccgp.config
{"baseUrl":"http://www.ccgp.gov.cn","initialUrl":"http://www.ccgp.gov.cn/","userAgent":"Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36"}

// ztb_gz.config
{"baseUrl":"http://ztb.guizhou.gov.cn","initialUrl":"http://ztb.guizhou.gov.cn/","userAgent":"Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36","xhrReferer":"http://ztb.guizhou.gov.cn/trade/?category=affiche"}
```

### 3.4 `notice.type` 枚举与频道映射

| 枚举值 | 中文 | CCGP 频道 | ztb_gz 频道（`noticeType`） |
|---|---|---|---|
| `tender` | 公开招标 | `/cggg/dfgg/gkzb/`（地方-公开招标） | `A01` 招标公告（另见 4.2 的 BTypeCode 码表） |
| `win` | 中标公告 | `/cggg/dfgg/zbgg/`（地方-中标公告） | `A04` 中标结果公示 |
| `change` | 更正公告 | `/cggg/dfgg/gzgg/`（地方-更正公告） | `A02` 变更公告 |
| `explore` | 询价公告 | `/cggg/dfgg/xjgg/`（地方-询价公告） | — |

CCGP 侧 `type` 由频道配置直接决定，不做二次推断；ztb_gz 侧经过三级降级链，频道 `type` 只是最后兜底。

## 四、已接入源站详解

### 4.1 中国政府采购网（`ccgp`）—— HTML 源

`CcgpSourceAdapter`，`code() = "ccgp"`，`@Component`，站点 `http://www.ccgp.gov.cn`。

**列表页 URL 规律**：第 1 页 = `baseUrl + channel.path`；第 n 页（n ≥ 2）= `baseUrl + channel.path + "index_" + n + ".htm"`。源码为 `String listUrl = baseUrl + channel.path + (page == 1 ? "" : "index_" + page + ".htm");`。详情相对链接形如 `<a href="./202609/t20260908_27283358.htm" title="标题">`，拼装规则 `baseUrl + channel.path + href.substring(2)`（剥掉开头 `./`）。

**抓取实现**：`java.net.http.HttpClient` + `CookieManager`（连接超时 15s、请求超时 20s、`Redirect.NORMAL`、响应按 UTF-8 解码、非 2xx 或异常一律返回 `null`）。

- **必须先预热**：以浏览器 UA 先 GET `initialUrl`（`http://www.ccgp.gov.cn/`）拿 Cookie，否则后续列表/详情会 403 或被频繁访问限流 —— 类注释第 1 条即写明。
- 请求头：`User-Agent`（配置或默认 UA）、`Accept-Language: zh-CN,zh;q=0.9`、有值时的 `Referer`。
- **`Referer` 链式推进**：每抓完一个列表页就 `referer = listUrl`，因此该频道所有详情请求的 `Referer` 都是本频道列表页，模拟「从列表点进详情」的正常用户路径。

**列表解析正则原文**：

```java
/** 列表项链接: <a href="./202609/t20260908_27283358.htm" title="标题"> */
private static final Pattern LIST_ITEM =
        Pattern.compile("<a href=\"(\\./[^\"?]+\\.htm)\"[^>]*title=\"([^\"]+)\"");
```

`[^\"?]+` 排除带查询串的链接；`group(1)` 是相对路径（本适配器只取 group(1)，标题由详情页解析得到）。候选 URL 收进 `LinkedHashSet<String>`，天然按插入序去重。

**详情字段锚点**（`CcgpNoticeParser.parse(String html, String type, String sourceUrl, String source)`，锚点均为 2026-09-08 实测）：

| 字段 | 提取方式（源码原文） |
|---|---|
| `title` | `<h2[^>]*class="tc"[^>]*>([^<]+)</h2>`；取不到时回落正文 `项目名称[：:]\s*([^<\n]+)`，再取不到则空串 |
| `projectNo` | `项目编号[：:]\s*([^<\s]+)` |
| `budget` | `预算金额[：:]\s*([\d,]+(?:\.\d+)?)\s*元`；再 `new BigDecimal(amount.replace(",", "")).divide(BigDecimal.valueOf(10000), 2, RoundingMode.HALF_UP)` —— **元 → 万元，HALF_UP，2 位小数** |
| `tenderPerson`（采购人） | `noticePurchase-purchaserOrgName[^>]*>\s*([^<]+)<` |
| `contactPhone`（采购人电话） | `noticePurchase-purchaserLinkTel[^>]*>\s*([^<]+)<` |
| `agency`（代理机构） | `noticeAgency-agencyName[^>]*>\s*([^<]+)<` |
| `contact`（项目联系人） | `projectContact-managerName[^>]*>\s*([^<]+)<` |
| `deadline` / `openTime` | `bidFileSubmitTime3[^>]*>\s*([^<]+)<` |
| `publishTime` | `name="releaseDateSpan"[^>]*>\s*([^<]+)<`；解析失败回落 `LocalDateTime.now()` |
| `content` | 优先 `id="noticeArea"`（新模板，截到其后的 `</style>` 之后）；**兜底** `vF_deail_maincontent`（旧/更正模板，源码即为此拼写 —— deail 少一个 t，是源站旧模板真实类名）：先回退到最近完整 `<div` 起点（仅当 `start - divStart <= 60`，避免残留类名文本），再在 `vF_detail_relcontent`（相关推荐栏）**之前截断**；最后统一在 `</div></div>` 收口 |
| `source` / `sourceUrl` | 入参：`site.getName()` 与详情页绝对 URL（去重键） |

日期统一走 `FULL_DATE_TIME = (\d{4})年(\d{1,2})月(\d{1,2})日\s*(?:(\d{1,2})时(\d{1,2})分)?`，只有日期时取当日 00:00。

**`deadline` 与 `openTime` 同值**是设计事实而非抓取遗漏 —— CCGP 正文只提供一个「投标文件递交截止时间」锚点，源码注释即 `// 4) 投标截止/开标时间(CCGP 公开招标: 开标时间=投标截止)`，随后 `setDeadline(deadline)` 后紧跟 `setOpenTime(deadline)`。这与 ztb_gz 不同（后者分别锚「投标截止时间」与「开标时间」）。

### 4.2 贵州省招标投标公共服务平台（`ztb_gz`）—— JSON 接口源

`GuizhouZtbSourceAdapter`，`code() = "ztb_gz"`，`@Component`，站点 `http://ztb.guizhou.gov.cn`。

> **关键区别：这是 JSON 接口源，不是 HTML 源。** 列表与详情都返回 JSON，没有可解析的 HTML 列表页。因此两段式的实现与 CCGP 不同：第一段调 search 取 `data[].Id`，第二段调 `GetDetail/{Id}` 取结构化 JSON；字段解析靠 JSON 字段 + 正文纯文本锚点正则，而非 HTML DOM 锚点。

**列表接口**完整 URL 模板（源码字面拼接）：

```
{baseUrl}/api/trade/search?pubDate=all&pubType=all&region=all&industry=all&prjType=all&noticeType={channel.path}&noticeClassify=all&pageIndex={n}&args=
```

| 参数 | 取值 | 含义 |
|---|---|---|
| `pubDate` / `pubType` | `all` | 发布日期范围 / 公告大类，全时段、全部 |
| `region` / `industry` / `prjType` | `all` | 地区、行业、项目类型均不筛选（地区靠 `RegionCode` 后置映射，行业靠本地关键词词典） |
| `noticeType` | `channel.path` | **公告类别编码**，来自 `channels` JSON 的 `path`（`A01` / `A02` / `A04`） |
| `noticeClassify` | `all` | 公告分类，全部 |
| `pageIndex` | `n` | 页码，从 1 开始 |
| `args` | 空 | 占位参数，保持与前端调用一致 |

响应处理：读 `totalNum`（`root.path("totalNum").asInt(0)`）与 `data` 数组；`totalNum == 0` 时置 `listEmpty` 标记并打日志。数组每项取 `Id`（`item.get("Id")`，为 null 或 `isNull()` 则跳过），拼成 `baseUrl + "/api/trade/GetDetail/" + Id` 放进 `LinkedHashSet`。细节：`listFetched` 在**请求返回后无条件累加**（`listJson == null` 也先加），`listParsed` 只在解析出条目时累加。

**详情接口与入库 URL**：详情请求 `GET /api/trade/GetDetail/{Id}`（常量 `DETAIL_PATH = "/api/trade/GetDetail/"`）。**入库的 `sourceUrl` 是展示页而非接口 URL** —— 源码用 `BULLETIN_PATH = "/trade/bulletin/?id="` 拼出 `baseUrl + BULLETIN_PATH + id` 传给解析器。

**为什么存展示页 URL**：`source_url` 既是去重唯一键，也是给终端用户看的溯源链接（用户端「查看原文」直接跳转）。接口 URL 对用户毫无意义（返回裸 JSON），且 `GetDetail` 属源站内部实现，改版时极易失效；展示页 URL 人类可读、长期稳定、可直接点击。用展示页 URL 去重同样成立 —— `Id` 与 `?id=` 一一对应。另注：详情成功后 `id` 是从**详情 JSON 自身**的 `Id` 字段重取的（`detail.path("Id").asText("")`），不是复用 URL 里的字符串。

**请求要求**：`fetch(client, url, ua, referer, boolean xhr)` —— 除与 CCGP 相同的 `User-Agent` / `Accept-Language` / 连接超时 15s / 请求超时 20s / `Redirect.NORMAL` / UTF-8 / 非 2xx 返回 null 外，另加：`Accept: application/json, text/javascript, */*; q=0.01`（模拟 jQuery XHR）、`Referer` = `xhrReferer`（默认 `{base}/trade/?category=affiche`）、以及仅当 `xhr = true` 时的 `X-Requested-With: XMLHttpRequest`。**Cookie 预热**：采集开始时对 `initialUrl` 发一次**不带 XHR 头**的请求（`fetch(..., false)`），失败仅记 warn 不中断 —— 注释为 `首页预热失败(不影响详情接口)`，因详情接口不强依赖会话 Cookie。

**失败重试与休眠**：详情失败**重试 1 次**，重试前先 `Thread.sleep(intervalMs)`（注释：`重试一次(限流场景)`），两次都失败才 `detailFailed++`。列表翻页间也休眠：`if (page < channel.pageCount) { Thread.sleep(intervalMs); }`；详情条间为 `if (idx > 0 || fetched > 0) { Thread.sleep(intervalMs); }` —— **首条也睡一次**，与 CCGP 的「首条不睡」不同。

**类型映射规则（重点）** —— 三级降级链：

```
   detail.BTypeCode（A01 / A02 / A04 …）
        ├─ 命中 TENDER_CODES → tender
        ├─ 命中 CHANGE_CODES → change
        ├─ 命中 WIN_CODES    → win
        └─ 未命中 ─────────────┐
                               ▼
   detail.BTypeCategory（affiche / publicity）
        ├─ "publicity" → win
        ├─ "affiche"   → tender
        └─ 其他 ───────────────┐
                               ▼
   channel.type（crawler_site.channels[].type）
        └─ fallback != null ? fallback : "tender"
```

码表原文（来源为源站 `allInfoCategorys`）：

```java
private static final String[] TENDER_CODES = {"A01", "A00", "D01", "D00", "D0A", "D41", "D40", "D4A", "Z01", "B01", "C01"};
private static final String[] CHANGE_CODES = {"A02", "A05", "D02", "D04", "D42", "D44", "Z02", "Z04", "AP2"};
private static final String[] WIN_CODES = {"A03", "A04", "D03", "D43", "Z03", "B02", "C02"};
```

判定：`BTypeCode` 非 null 时依次扫三张表（顺序 tender → change → win）；全未命中再看 `BTypeCategory` 字面值；仍未知才用频道 `type`，最后兜底 `"tender"`。取舍：`BTypeCode` 粒度最细最准故优先；`BTypeCategory` 只有「公告/公示」两档，粒度粗但稳定；频道 `type` 是人工先验，仅在前两者异常时启用。三档并存使源站新增类别码时**类型不会丢失**（退到第二档）。

**字段提取**：详情 JSON 自带字段（类注释列出）`Id`、`AfficheId`、`Title`、`ReadCount`、`BTypeCategory`、`BTypeCode`、`ProjectType`、`RegionCode`、`PublishBy`、`PublishDate`、`Source`、`Content`、`UnifiedDealCode`、`Summary`、`UploadFile`、`PdfFile`。结构化字段（预算/截止时间/招标人等）源站**无独立字段**，全部从 `Content` 去标签后的纯文本用中文锚点正则提取：

| 字段 | 正则原文 |
|---|---|
| `projectNo` | `(项目编号\|招标编号\|交易编号\|统一交易码)[：:]?\s*([A-Za-z0-9][A-Za-z0-9-]{4,})` |
| `budget` | `(预算金额\|项目预算\|采购预算)[：:]?\s*([\d,]+(?:\.[\d]+)?)\s*(元\|万元\|万)` |
| `tenderPerson` | `(招标人\|采购人\|建设单位\|招标单位)[：:]\s*([^\s。；]{2,})` |
| `agency` | `(招标代理机构\|代理机构\|招标代理)[：:]\s*([^\s。；]{2,})` |
| `contact` | `(项目联系人\|联系人)[：:]\s*([^\s。；]{2,})` |
| `contactPhone` | `(联系电话\|电话)[：:]?\s*([\d-]{6,14})` |
| `deadline` | `(投标截止时间\|递交截止时间\|截止时间)\s*?(\d{4}[年/-]\d{1,2}[月/-]\d{1,2}日?)` |
| `openTime` | `(开标时间\|开标日期)\s*?(\d{4}[年/-]\d{1,2}[月/-]\d{1,2}日?)` |

（表中 `\|` 表示正则里的 `|`，源码是普通 `|`。）要点：

- `projectNo` **优先取源站 `UnifiedDealCode`**，为空才回落正文正则。
- `agency` **兜底源站的 `Source` 字段**（发布机构），即 `notEmpty(first(AGENCY, plain)) ? first(AGENCY, plain) : text(detail, "Source")`。
- `budget` 带单位处理：单位 `元` 时 `÷10000`（HALF_UP，2 位）折万元；单位 `万元`/`万` 时**原样保留**。例：`预算金额：296000.00元` → `29.60`；`预算金额：120万元` → `120.00`。
- `publishTime` 取 `PublishDate`（`yyyy-MM-dd`），缺失或解析失败回落 `LocalDateTime.now()`。
- **去标签是删除而非替换空格**：`html.replaceAll("<[^>]+>", "")` 后替换 `&nbsp;`→空格、`&amp;`→`&`、`&ldquo;`→`“`、`&rdquo;`→`”`。源码注释指出「ztb 正文 `<span>` 会打断纯文本，必须移除而非替换空格」—— 否则「项<span>目</span>编号」会被拆断导致锚点失配。
- `first()` 取 `matcher.group(matcher.groupCount() >= 2 ? 2 : 1)` —— 有两个捕获组时取**第 2 组**（值），这正是上表锚点正则都用「锚 + 值」双组的原因。

**地区**：`province` **硬编码 `"贵州"`**（该站即贵州省平台）；`city` 由 `RegionCode` 前缀查 `GZ_REGION_CITY`：

| RegionCode 前缀 | 520100 | 520200 | 520300 | 520400 | 520500 | 520600 | 522300 | 522600 | 522700 | 520000 |
|---|---|---|---|---|---|---|---|---|---|---|
| 城市 | 贵阳市 | 六盘水市 | 遵义市 | 安顺市 | 毕节市 | 铜仁市 | 黔西南州 | 黔东南州 | 黔南州 | （空串，省级） |

查找逻辑 `regionCity(regionCode)`：先取前 6 位精确匹配；不中则取前 4 位 + `"00"` 再匹配一次（省级码 → `520000` → 空串）；都不中返回 `""`。源站 `RegionCode` 原值同时写入 `notice.region_code` 保留溯源。

> ### ⚠ 现状告警：源站列表接口当前不可用
> `GuizhouZtbSourceAdapter` 类注释原文（实测记录 2026-09-08）：
> ```
> ⚠️ 2026-09-08 实测: search 接口对外返回 totalNum=0(源站列表数据下线),
> GetDetail/{Id} 可用。源站恢复后本适配器零改动即可采集。
> ```
> 即 `/api/trade/search` 返回 `totalNum = 0`、`data` 为空数组 → 采集走到列表阶段就结束：`listFetched` 累加、`listParsed = 0`、任务 `SUCCESS` 但 `newInsert = 0`；而 `GetDetail/{Id}` 仍正常（给定已知 Id 能取到完整 JSON）。
> 这是**源站侧数据下线，不是适配器缺陷** —— 代码路径、URL 模板、字段映射均已实测正确。源站一旦恢复放量，**适配器无需任何改动**即可自动采到数据，这正是「配置驱动 + 适配器隔离」的价值所在：外部变化被隔离在一个文件里，而这个文件当前不需要改。
> 因此截至 2026-09-08，两个已接入站点中**仅 `ccgp` 实际产出数据**。运维上不必为 ztb_gz 的 0 条新增告警，但应关注该站接口是否恢复。

## 五、归一化处理

由 `NoticeRegionExtractor`（`public final` 静态工具类，两解析器共用）承担，全部为**规则推导**。

### 5.1 地区提取 `extractRegion(text)`

入参 = `标题 + " " + 正文纯文本`，返回 `String[]{province, city}`。

**省份**：31 项 `PROVINCES` 数组（4 直辖市 + 27 省/自治区），逐项 `text.indexOf(name)`，取 `idx >= 0 && idx < bestIdx` 的**最早命中**者（按文本位置，不是数组顺序）。命中后剥离后缀：`province = name.replace("自治区", "").replace("省", "").replace("市", "")` —— 故「广西壮族自治区」→「广西」、「贵州省」→「贵州」、「北京市」→「北京」。31 项原文：

```
北京市, 天津市, 上海市, 重庆市, 河北省, 山西省, 内蒙古自治区, 辽宁省, 吉林省, 黑龙江省,
江苏省, 浙江省, 安徽省, 福建省, 江西省, 山东省, 河南省, 湖北省, 湖南省, 广东省,
广西壮族自治区, 海南省, 四川省, 贵州省, 云南省, 西藏自治区, 陕西省, 甘肃省, 青海省,
宁夏回族自治区, 新疆维吾尔自治区
```

**城市**：正则 `Pattern.compile("([一-龥]{2,12}?市)")`（非贪婪）逐个尝试；**仅在满足以下之一时才采纳**：① 候选（去「市」后）在 `CITY_PROVINCE` 词典中（**102 条**，覆盖 31 个省级区划）；② 或属 4 个直辖市 `"北京"` / `"天津"` / `"上海"` / `"重庆"`。命中即 `break`（取文本中最早出现的**合法**城市）。若此时 `province` 仍为空，用词典映射的省填充；直辖市用候选自身（**直辖市 province = city**）。

**为什么要加词典约束**：中文公告里「某某市」字符串极多，机构名、厂名都可能以「市」结尾（「某某市医院」「城市管理局」片段），纯正则会把这类字符串误判为城市，且 `{2,12}?` 非贪婪还会切出奇怪片段。加一层「必须是真实已知城市」的白名单后误判率大幅下降；代价是词典外的地级市（如「鄂尔多斯」「克拉玛依」）取不到 `city` —— 此时 `province` 通常仍能从 `PROVINCES` 命中，属可接受折中。

**空值兜底**：`province` 与 `city` 都为空时 `province = "其他"`；返回时再兜一层 `province.isEmpty() ? "其他" : province`。故 `province` **永不为空**，`city` 可为空串。

### 5.3 正文转纯文本 `toPlainText(html)`

`html.replaceAll("<[^>]+>", " ").replaceAll("&nbsp;", " ").replaceAll("&amp;", "&")`，供关键词匹配使用。注意它**与 ztb_gz 解析器内部的 `stripTags` 不是同一实现**：`toPlainText` 把标签替换为**空格**（保留词边界，利于 `detectIndustry` 的 `contains` 不跨标签误拼），`stripTags` 是**删除**标签（用于锚点正则，避免 `<span>` 打断连续中文）。

### 5.4 诚实标注局限

- 地区与行业均为**规则推导结果，不是源站官方字段**。省份依赖文本中首次出现的省名（若正文先提「参照北京市标准」而项目在湖北，会判成北京）；城市受限于 102 条词典；行业受限于 15 行词典覆盖且存在优先级竞争。
- 两者兜底值均为 `"其他"`，用户端应把「其他」视作「未识别」而非真实分类。种子数据中也存在词典外取值（如 id=7 的 `科研设备`，另有 `智慧城市`、`机关团体`），属历史演示数据。
- `content` 存的是**正文富文本片段**，**不是源站原始页面 HTML** —— 平台对采集数据做加工，详情页抓回来后只截公告正文区段入库：CCGP 从 `id="noticeArea"` 起截（`extractContent()`，并剔除其后的 `</style>` 块），旧模板兜底 `vF_deail_maincontent` 且截到相关推荐栏 `vF_detail_relcontent` 前；ztb_gz 直接取源站 JSON 的 `Content` 字段。页面骨架（导航/页头页脚/侧栏/面包屑）、相关推荐、广告与脚本**在入库前就被丢弃**，不落库、不留存；附件（`UploadFile`/`PdfFile`）同样忽略。
- 但**片段内未做标签白名单清洗**：截取后的富文本原样送前端 `v-html` 渲染，依赖源站自身可信度 —— 与 `tender.xss.enable: false` 是同一取舍。这是当前已知不足，公网部署前应评估是否需要按标签白名单过一遍。

## 六、去重与更新（upsert）

### 6.1 唯一键与判定流程

唯一键 `notice.source_url`（DDL：`UNIQUE KEY uk_source_url (source_url)`；MySQL 唯一索引允许多个 NULL，故未采集的种子数据不冲突）。流程：

```
解析后 NoticePortalDO
   ▼ noticePortalMapper.selectBySourceUrl(sourceUrl)
   ├─ 不存在 → insert(notice)                                    newInsert++
   └─ 已存在 → 逐字段比对 title / deadline / budget / content /
                province / city / industry
                ├─ 有变更 → 复制整套字段到 existing 后 updateById   updated++
                └─ 无变更 → 跳过（不计任何计数）
```

- **insert 分支**：直接 `insert` 新构造的 DO，`stats.newInsert++`。
- **update 分支**：比对 **7 个字段**（`title`、`deadline`、`budget`、`content`、`province`、`city`、`industry`）决定是否更新；更新时**复制全套 14 个字段**（`title`、`content`、`deadline`、`openTime`、`budget`、`tenderPerson`、`agency`、`contact`、`contactPhone`、`projectNo`、`publishTime`、`province`、`city`、`industry`）后 `updateById(existing)`，`stats.updated++`。
- **为什么「检测 7 个、更新 14 个」**：检测集是「会随时间变化且对用户有意义」的字段（更正公告改 deadline 与正文；重采可能使 budget/地区/行业识别结果变化）；更新集则把整条记录刷成最新，避免出现「一半新一半旧」的脏状态。更新在 `existing` 对象上进行，**保留原 `id` 与 `sourceUrl`**，不产生新行。
- 比对用 `equalsSafe`：`a == null ? b == null : a.equals(b)`，正确处理 `BigDecimal`、`LocalDateTime` 的 null。**无变更时不写库、不计任何计数器**，故「`newInsert = 0` 且 `updated = 0`」是重复采集一轮的正常结果。

### 6.2 实现载体：`NoticeUpsertService`

> 2026-09-11 已还债：上述 `upsert`（含 `equalsSafe`）原在 `CcgpSourceAdapter` 与 `GuizhouZtbSourceAdapter` 中**各写了一份**，两份逐字节相同。现上提为共享组件 `tender-module-crawler/.../service/NoticeUpsertService.java`，两个适配器改为 `@Resource` 注入后调用 `noticeUpsertService.upsert(notice, stats)`，适配器自身不再持有 `NoticePortalMapper`。
>
> 附带修正：ccgp 版原多一行重复的 `existing.setOpenTime(...)`（同一 setter 连调两次），合并时去掉。
>
> **接入新源站时直接注入该服务即可，不要再复制 upsert 逻辑。**

### 6.3 为什么以 URL 而非项目编号去重

1. **各站格式不一**：CCGP 的编号是「项目编号：」后的一串字符（可能含中文、括号），ztb_gz 优先取 `UnifiedDealCode`（统一交易码），编码体系完全不同、跨站不可比。
2. **常常缺失**：`projectNo` 从正文正则捞出，源站不写就没有；ztb_gz 的 `UnifiedDealCode` 也常见为空。用它做唯一键会让大量记录退化成空串，无法区分。
3. **同项目有多份公告**：一个项目会发招标公告、更正公告、中标公告 —— 编号相同但应是三条独立记录（`type` 不同），用编号去重会误合并。
4. **URL 稳定唯一**：源站每篇公告有且只有一个详情页地址，是天然主键，且正是用户溯源要用的链接 —— 一次满足「幂等重采」与「可点击溯源」两个需求。

## 七、调度与并发控制

### 7.1 手动触发

`CrawlerController`（`@RequestMapping("/crawler")` → 实际前缀 `/admin-api/crawler`）的 `POST /run`，签名 `CommonResult<Long> run(@RequestParam(value = "siteCode", required = false) String siteCode)`，类注释标注 `DEMO: PermitAll 匿名可调,正式版需管理员鉴权`。

- `POST /admin-api/crawler/run?siteCode=ccgp` 触发单站点；不传 `siteCode` 则采集**所有 `enabled = 1` 的站点**。
- **立即返回任务 id**（首个站点的 `crawler_task.id`），采集在后台线程异步执行，前端拿 id 后轮询。
- `siteCode` 不存在抛 `CRAWLER_SITE_NOT_EXISTS`，存在但停用抛 `CRAWLER_SITE_DISABLED`。

### 7.2 定时触发

`ScheduledCrawlTask.runAllSites()`：

```java
@Scheduled(cron = "${tender.crawler.schedule-cron:0 0 */2 * * ?}")
@TenantIgnore // 定时线程非 HTTP 请求, 需显式忽略租户上下文(与 TokenCleanJob 一致)
```

- cron 默认 `0 0 */2 * * ?`（Spring 6 段，秒在前），即**每 2 小时整点**一轮；运行时由 `CrawlerProperties.scheduleEnabled`（`tender.crawler.schedule-enabled`，默认 `true`）开关控制，方法体首行即 `if (!crawlerProperties.isScheduleEnabled()) { ...; return; }`，随后 `crawlService.run(null)`。**不能用「把 cron 设空」来关停** —— 源码注释：「cron 设为空/OFF 会导致启动报错，关闭定时请用本开关」。
- **`@TenantIgnore` 的必要性**：Spring 调度线程没有 HTTP 请求上下文，也就不存在租户上下文，MyBatis 租户拦截器在写 `crawler_task` / `notice`（两表均有 `tenant_id`）时会尝试取当前租户 id 而 **NPE**。加注解让框架在该线程跳过租户处理，是本项目多租户框架下的强制约定，与既有 `tokenCleanJob` 一致。

> **已知待改进项：它是 Spring 原生 `@Scheduled`，不是 Quartz。**
> 因此它**不在 `infra_job` 表里**，`tender-module-infra` 的定时任务管理页面不存在这个任务；**管理端无法启停、无法改 cron、无法看执行日志、无法手动「执行一次」**（管理端能点的「采集全部/立即采集」走的是 `POST /crawler/run`，与 cron 无关）。调整周期必须改 `application.yaml` 并重启，临时停用只能靠开关 + 重启。另注：local profile 显式排除了 `QuartzAutoConfiguration`，dev profile 才启用 Quartz —— 两种 profile 下定时采集都是 `@Scheduled` 行为，不随 Quartz 开关变化。改进方向是改造成 `infra_job` 注册的 JobHandler（`@TenantJob`），获得可运维的启停与日志。

### 7.3 四道并发护栏

**第 1 道 · 单线程守护线程池（全局串行）**：`Executors.newSingleThreadExecutor` 且 `Thread` 名为 `crawler-run`、`setDaemon(true)`（类注释：`采集线程池(单线程串行, 防止并发打爆源站)`）。保证**任意时刻全平台只有一个采集任务在跑**，无论提交多少站点；线程名便于日志检索，守护线程不阻塞 JVM 退出，且与 Web 请求线程池隔离 —— 采集再慢也不占满 Tomcat 线程。代价是站点数增长后总耗时线性叠加，当前 2 站点、3 秒间隔够用，上量后应改为「每站点一线程、站内串行」的有界线程池。

**第 2 道 · 站点级 RUNNING 任务守卫（防重入）**：`crawlTaskMapper.selectRunningCount(site.getCode()) > 0` 时 `log.warn` 并 `continue` 跳过提交（源码注释：`防重入: 该站点已有执行中的任务时跳过(定时 + 手动并发)`）。SQL 语义为 `COUNT(*) FROM crawler_task WHERE site_code = ? AND status = 'RUNNING' AND deleted = 0`。拦住「12:00 定时正在跑 ccgp，运维又手动点了 ccgp」的场景 —— 不会重复入库（即使进去 upsert 也幂等，但会浪费源站请求）。

**第 3 道 · 超时任务回收（防僵尸）**：`run()` 的**最开头**执行 `crawlTaskMapper.failStaleTasks(Duration.ofHours(4))`（注释：`每轮先回收卡死的 RUNNING 任务(进程崩溃后遗留,避免永久挡住该站点)`）—— 把所有 `status = RUNNING` 且 `start_time < now - 4h` 的任务置为 `FAILED`、`error_msg = '超时自动回收'`，并补 `end_time`。这解决第 2 道护栏的副作用：进程若在采集中途被 kill，那条 RUNNING 记录会永久挡住该站点（`selectRunningCount > 0` 永远成立）。4 小时远大于单轮全量采集的正常耗时。

**第 4 道 · 站点级详情页间隔（频控）**：`crawler_site.interval_ms`，默认 3000ms。适配器在详情请求间 `Thread.sleep(intervalMs)`；ztb_gz 额外在列表翻页间与失败重试前也休眠（见 4.2）。

### 7.4 反爬策略汇总

| 策略 | 实现 |
|---|---|
| 浏览器 UA | `config.userAgent`，默认 Chrome 120 桌面 UA，规避空 UA / 爬虫 UA 被拦 |
| 首页 Cookie 预热 | 采集前 GET `initialUrl` 让 `CookieManager` 拿到会话 Cookie。CCGP **必须**（否则 403/限流），ztb_gz 失败可容忍 |
| `Referer` 链 | CCGP：详情请求带所属列表页 URL；ztb_gz：固定带 `xhrReferer`（默认 `{base}/trade/?category=affiche`） |
| 模拟 XHR | ztb_gz 对 `search` 与 `GetDetail` 带 `X-Requested-With: XMLHttpRequest` 与 jQuery 风格 `Accept` |
| 频控 | `interval_ms` 详情间隔 + 单线程全局串行（7.3 第 1、4 道） |
| 失败重试 | ztb_gz 详情失败重试 1 次（重试前休眠）；CCGP 不重试，直接计 `detailFailed` |
| 单条失败隔离 | 每条详情的解析异常被 try/catch 吞掉并计 `detailFailed`，不中断整轮采集 |

> **明确说明：当前没有分布式锁、没有 Redis 限流器、没有代理池。**
> - **不用分布式锁**：部署形态是单机单实例，第 1 道护栏（进程内单线程池）+ 第 2 道护栏（DB 级 RUNNING 守卫）已能保证串行。将来横向扩容成多实例时第 1 道会失效（每实例一个线程池），第 2 道仍能挡住「同站并发」，但它基于「查询 + 校验」两步且不在同一事务里，存在竞态窗口 —— 多实例下应改为加锁（lock4j 已在依赖中，`application-local.yaml` 配了 3000/30000）并把 `interval_ms` 提升为实例级随机抖动。
> - **不用 Redis 限流器**：源站级访问是低频的（一轮数分钟、每详情间隔 3 秒），单实例总请求速率本身受控，引入限流器对当前规模是过度设计。
> - **不用代理池**：请求量小、访问的是政府公开信息页，单 IP 低频访问不会触发封禁；引入代理池反而带来可用性与合规成本。
> 这些取舍的前提是**单机单实例 + 低频率**。扩容、提升采集频率或大幅增加站点数时需重新评估。

## 八、任务日志与可观测性（`crawler_task`）

### 8.1 表结构与列含义

| 列 | 类型 | 含义与写入时机 |
|---|---|---|
| `id` | bigint PK | 任务编号，DB 自增（`AUTO_INCREMENT=100` 起），`createTask` 时分配 |
| `site_code` | varchar(32) | 站点标识，关联 `crawler_site.code`；建任务时写入 |
| `start_time` | datetime | 开始时间，`createTask` 时 = `LocalDateTime.now()` |
| `end_time` | datetime | 结束时间，`runSite` 收尾时 = `LocalDateTime.now()`；超时回收时也补 |
| `status` | varchar(16) | `RUNNING` / `SUCCESS` / `FAILED`（枚举 `CrawlerTaskStatusEnum`），默认 `RUNNING`；建任务即 RUNNING，收尾置 SUCCESS/FAILED |
| `list_fetched` | int | 列表页抓取数，默认 0 |
| `list_parsed` | int | 列表解析出公告数（候选详情数），默认 0 |
| `detail_fetched` | int | 详情页抓取成功数，默认 0 |
| `detail_failed` | int | 详情页抓取失败数（含抓取失败与解析失败），默认 0 |
| `new_insert` | int | 新增入库数，默认 0 |
| `updated` | int | 变更更新数，默认 0 |
| `error_msg` | varchar(512) | 失败原因，默认 `''`，**写入前截断至 500 字符**；仅在 `crawl()` 抛异常时写入 |

另含 `BaseDO` 通用审计与逻辑删除列；`CrawlerTaskDO` 与列一一对应。

### 8.2 `CrawlStats` 计数器的递增时机

`CrawlStats` 是适配器与任务日志之间的**中转计数器**（`@Data`，6 个 `int`）。`runSite` 在 `crawl()` 返回后（无论成功失败）把这 6 个值整体复制到 `CrawlerTaskDO` 并 `updateById`。

| 计数器 | CCGP 递增时机 | ztb_gz 递增时机 |
|---|---|---|
| `listFetched` | 列表页 HTTP 返回非 null 且 2xx 时 +1 | **请求返回后无条件 +1**（含返回 null），实为「列表请求次数」 |
| `listParsed` | 正则匹配到的 `<a>` 条目数 | `data` 数组中 `Id` 非空且非 null 的条目数 |
| `detailFetched` | 频道循环结束时一次性累加本频道成功抓取数 | 同左 |
| `detailFailed` | 详情 HTTP 失败 +1；解析抛异常再 +1（两来源互斥，不重复计同一条） | 重试后仍失败 +1；解析抛异常 +1 |
| `newInsert` | `NoticeUpsertService.upsert` 中 `selectBySourceUrl` 返回 null（insert 分支）+1 | 同左 |
| `updated` | `NoticeUpsertService.upsert` 中判定 changed 为 true 时 +1 | 同左 |

读日志的一个细节：CCGP 的 `detailFailed` 在日志里被当**累计值**打印（`log.info("[crawler] 频道 {} 完成: 详情{}条/失败{}条", channel.path, fetched, stats.getDetailFailed())`），此处的「失败」是**任务累计**而非本频道值。

### 8.3 错误信息截断

```java
task.setErrorMsg(ex.getMessage() == null ? ex.getClass().getSimpleName()
        : ex.getMessage().substring(0, Math.min(500, ex.getMessage().length())));
```

`error_msg` 列宽 512，写入前硬截断到 500 字符留余量；`getMessage()` 为 null 时退化为异常类简单名（如 `NullPointerException`）。截断只在**整站点失败**时发生；单条详情失败的异常只进日志（`log.warn`），不写 `error_msg`。

### 8.4 管理端如何消费

| 端点（均 `@PermitAll`） | 用途 |
|---|---|
| `GET /admin-api/crawler/site/list` | 站点配置列表，返回 `CrawlerSiteRespVO`（`id`/`name`/`code`/`enabled`/`channels`/`intervalMs`；**`config` 不下发**，避免暴露 UA 等配置） |
| `GET /admin-api/crawler/task/latest?siteCode=` | 某站点最近一次任务（`selectBySiteCode` → `ORDER BY id DESC LIMIT 1`） |
| `GET /admin-api/crawler/task/page` | 任务日志分页（`PageParam` + 可选 `siteCode`，按 `id DESC`） |

前端页面 `admin-web/src/views/crawler/index.vue`（`defineOptions({ name: 'CrawlerCenter' })`，菜单 id 12800，path `/crawler`）：「采集全部」→ `runCrawler()`，站点卡片「立即采集」→ `runCrawler(item.code)`，成功提示 `采集任务 #${taskId} 已创建,稍后刷新查看`；卡片展示站点名、启用状态、站点标识、频道数（前端 `JSON.parse(channels).length`）、最近任务状态标签、最近新增/更新数、更新时间；下方表格展示任务编号、站点名、状态、列表/解析、详情/失败、新增/更新、开始/结束时间、错误信息。**页面每 5 秒轮询最近任务状态**：

```js
timer = window.setInterval(() => { refreshLatest() }, 5000)
```

`refreshLatest` 对每个站点并发调 `getCrawlerLatestTask`，刷新卡片状态与新增/更新数；`onBeforeUnmount` 中 `clearInterval` 清理。注意**只有卡片区在轮询**，下方任务表格不自动刷新（需手动「搜索」/「刷新」）。状态映射：`RUNNING` → 「执行中」/primary，`SUCCESS` → 「成功」/success，`FAILED` → 「失败」/danger。

### 8.5 一次成功采集的读法

```json
{ "id": 100, "siteCode": "ccgp", "status": "SUCCESS",
  "listFetched": 4, "listParsed": 87, "detailFetched": 85, "detailFailed": 2,
  "newInsert": 12, "updated": 3, "errorMsg": "" }
```

4 个频道各抓 1 页列表，共解析出 87 条候选；85 条详情抓取 + 解析成功、2 条失败（源站删页或模板异常）；其中 12 条新公告入库、3 条是已存在但字段有变（多为更正公告改期）。`newInsert` 与 `updated` 均为 0 说明源站无新公告，属正常。

## 十、合规与边界

采集对象是**政府公开发布**的招投标公告，边界明确：

1. **只抓公告正文页，不抓附件文件**：适配器只请求列表页与详情页 HTML/JSON，**不下载任何 `.pdf`/`.doc`/`.zip` 附件** —— 源站详情 JSON 里的 `UploadFile`、`PdfFile` 字段被有意忽略。招标文件应由投标人按官方流程在源站办理。
2. **只留用户关注的内容，不整页留存**：入库前即完成「截正文 + 抽字段」，`notice` 表里**没有原始 HTML 页面**；`content` 只是公告正文片段，页面骨架、样式块、推荐位、广告脚本一律不落库。即平台对数据是**有加工**的（截取 + 结构化），但**加工只做取舍与归集，不做改写**（见第 6 条）。
3. **保留溯源信息**：每条 `notice` 都带 `source`（来自 `crawler_site.name`）与 `source_url`（源站展示页 URL），用户看到的每条公告都能一键跳回原始出处；`region_code` 保留源站原始地区码。这是政府信息公开场景下的必要标注。
4. **遵守 robots 协议**：接入新站前先查看 `/robots.txt`，`Disallow` 的路径不采。当前两个站点采集的都是公开公告栏目，未触碰需授权区域（如用户中心、投标系统后台）。
5. **控制访问频率**：四道并发护栏（7.3）+ `interval_ms` 默认 3 秒详情间隔，把访问速率压到远低于人工浏览水平；单机单实例部署天然不形成并发压力。**不追求「实时」，只要求「不漏」** —— 两小时一轮对招投标场景完全满足时效需求。
6. **不做知识产权数字化传播**：正文片段仅**截取**用于阅读与检索，不做二次创作、不做商业分发、不绕过源站任何访问控制或付费墙。平台定位是**信息聚合与检索入口**，法律效力以政府官网公告为准（与 [`09-数据源清单.md`](../数据/09-数据源清单.md) 的「法定平台」口径一致）。
7. **不采集非公开数据**：不模拟登录、不使用账号凭据、不抓取需身份认证的内容。ztb_gz 的 Cookie 仅为访问公开接口所需的会话标识，不涉及登录态。
