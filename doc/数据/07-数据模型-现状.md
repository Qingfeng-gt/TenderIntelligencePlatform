## 一、总览

当前数据库 `tender` 中，本项目**自建的业务表共 5 张**，另有框架自带表若干。业务表全部集中在一个 DDL 文件里：

| DDL 文件 | 表名 | 中文名 | 所属模块 | 说明 |
|---|---|---|---|---|
| `notice.sql` | `notice` | 招投标公告（标讯） | `tender-module-notice` | 核心表。多源采集归一后的公告数据，用户端检索的唯一数据来源 |
| `notice.sql` | `crawler_site` | 爬虫站点配置 | `tender-module-crawler` | 站点/频道/频控配置，**配置驱动，改这里不改代码** |
| `notice.sql` | `crawler_task` | 采集任务日志 | `tender-module-crawler` | 每次采集的统计与结果，管理端「数据采集中心」消费 |
| `notice.sql` | `bid_project` | 投标项目 | `tender-module-bid` | 用户投标闭环，带状态机 |
| `tender.sql` | `member_user` | 会员用户 | `tender-module-member` | 用户端（`user-web`）账号，与后台 `system_users` 完全隔离 |

框架自带表（`tender.sql`，共 24 张）为 `infra_*`（11 张：API 访问/异常日志、代码生成器、配置、数据源、文件、文件存储、文件内容、定时任务定义、任务日志）、`system_*`（13 张：字典数据/类型、登录日志、菜单、站内公告、站内信、通知模板、操作日志、角色、角色菜单、用户角色、用户）等。这些是脚手架能力的承载表，不属于本项目业务设计，不在本文展开。

> ⚠️ `notice.sql` 与 `tender.sql` 均为 **DROP + CREATE 全量初始化脚本**，无增量演进片段，只用于新库初始化或整体重置。执行顺序必须是先 `tender.sql` 后 `notice.sql`。

## 二、业务表详解

### 2.1 `notice` —— 招投标公告（标讯）表

> DDL 位置：`backend/sql/mysql/notice.sql` 第 16-45 行
> DO 映射：`tender-module-notice/.../dal/dataobject/NoticePortalDO.java`（`@TableName("notice")`）

**表说明**：全平台的核心数据表。四个源频道采集回来的公告，经适配器解析、地区/行业归一后统一落到这里，用户端首页、列表页、详情页全部读这张表。

| 字段名 | 类型 | 允许空 | 默认值 | 注释 |
|---|---|---|---|---|
| `id` | bigint(20) | 否 | AUTO_INCREMENT | 公告编号 |
| `title` | varchar(512) | 否 | `''` | 公告标题 |
| `project_no` | varchar(128) | 否 | `''` | 项目编号（源站，如 `SXSD2026-AK-056`） |
| `type` | varchar(16) | 否 | `''` | 公告类型：`tender` 招标 / `win` 中标 / `change` 变更 / `explore` 采购 |
| `province` | varchar(32) | 否 | `''` | 省份（**规则推导**，非源站官方字段） |
| `city` | varchar(32) | 否 | `''` | 城市（**规则推导**） |
| `industry` | varchar(64) | 否 | `''` | 行业（**规则推导**，如 市政工程/医疗卫生） |
| `budget` | decimal(18,2) | 是 | NULL | 预算金额（**万元**；源站多为「元」，采集时 ÷10000 换算） |
| `tender_person` | varchar(128) | 否 | `''` | 招标人 / 采购人 |
| `agency` | varchar(128) | 否 | `''` | 代理机构 |
| `contact` | varchar(64) | 否 | `''` | 联系人 |
| `contact_phone` | varchar(32) | 否 | `''` | 联系电话 |
| `content` | longtext | 是 | NULL | 公告正文**富文本片段**（采集时从详情页截取正文区段，**非源站原始页面 HTML**；前端 `v-html` 渲染） |
| `source` | varchar(128) | 否 | `''` | 来源网站（如「中国政府采购网」） |
| `source_url` | varchar(512) | 是 | NULL | 源站详情 URL —— **唯一去重键** |
| `publish_time` | datetime | 否 | — | 发布时间 |
| `deadline` | datetime | 是 | NULL | 投标截止时间 |
| `open_time` | datetime | 是 | NULL | 开标时间 |
| `region_code` | varchar(16) | 否 | `''` | 源站地区代码（如贵州的 `520100`） |
| `creator` / `create_time` / `updater` / `update_time` / `deleted` / `tenant_id` | — | — | — | 公共字段，见 §三 |

**索引**：

| 类型 | 名称 | 字段 | 用途 |
|---|---|---|---|
| PRIMARY | `PRIMARY` | `id` | — |
| UNIQUE | `uk_source_url` | `source_url` | **去重唯一键**。MySQL 唯一索引允许多个 NULL，故未回填 URL 的记录不受约束 |
| KEY | `idx_type_publish` | (`type`, `publish_time`) | 列表页「按类型 + 时间倒序」主查询路径 |
| KEY | `idx_province` | `province` | 地区筛选 |
| KEY | `idx_industry` | `industry` | 行业筛选 |
| KEY | `idx_publish_time` | `publish_time` | 「今天发布」计数与时间区间检索 |

**关键设计说明**：

1. **为什么以 `source_url` 而非 `project_no` 去重**：项目编号各源站格式不一（ccgp 叫「项目编号」、ztb_gz 有 `UnifiedDealCode`/交易编号等多种叫法）且经常缺失；URL 稳定唯一且天然携带来源信息。`project_no` 仅作人工核对辅助。
2. **`province`/`city`/`industry` 是推导值**：由 `NoticeRegionExtractor` 按词典与正则从标题/正文中提取，**不是源站官方字段**，会有误判，兜底值为「其他」。详见 [`06-数据采集设计.md`](../技术/06-数据采集设计.md) §五。
3. **`budget` 单位为万元**：源站原始单位以「元」为主，入库前统一换算（÷10000，HALF_UP，保留 2 位）。前端展示时直接按万元渲染。
4. **`content` 存 HTML 而非纯文本**：为了保留公告排版（表格、加粗、段落），前端用 `v-html` 渲染。XSS 风险由 `tender.xss.enable` 控制（当前为 `false`）。
5. 无 `view_count` 字段 —— 浏览量统计尚未实现。

**种子数据**：20 条（`id` 1-20），覆盖 tender/win/change/explore 四类，标题与 HTML 正文与 `user-web` 的演示数据对齐，供开发联调；正式数据由采集写入。`AUTO_INCREMENT = 100`，为种子数据预留了 1-99 的空间。

### 2.2 `crawler_site` —— 爬虫站点配置表

> DDL 位置：`backend/sql/mysql/notice.sql` 第 77-94 行
> DO 映射：`tender-module-crawler/.../dal/dataobject/CrawlerSiteDO.java`

**表说明**：这是采集系统的**配置驱动核心**。接入一个新源站，除了实现 `SourceAdapter` 接口外，只需在这张表插一行，无需改动 `CrawlService`、定时任务或管理端页面。

| 字段名 | 类型 | 允许空 | 默认值 | 注释 |
|---|---|---|---|---|
| `id` | bigint | 否 | AUTO_INCREMENT | 站点编号 |
| `name` | varchar(64) | 否 | — | 站点名称 |
| `code` | varchar(32) | 否 | — | 站点标识，**对应 `SourceAdapter.code()` 实现** |
| `enabled` | bit(1) | 否 | `b'1'` | 是否启用（`run` 不带 siteCode 时只跑启用的站点） |
| `channels` | varchar(1024) | 否 | `''` | 频道 JSON：`[{path,name,type,pageCount}]` |
| `interval_ms` | bigint | 否 | `3000` | 详情页请求间隔（毫秒，防反爬） |
| `config` | varchar(2048) | 否 | `''` | 抓取配置 JSON：`baseUrl` / `initialUrl` / `userAgent` / `xhrReferer` |
| 公共字段 | — | — | — | 见 §三 |

**索引**：`PRIMARY (id)`、`UNIQUE uk_code (code)`（保证站点标识唯一）。

**`channels` JSON 字段语义**：

| 键 | 含义 |
|---|---|
| `path` | 频道路径（HTML 源）或类别编码（接口源）。ccgp 用路径，ztb_gz 用 `noticeType` 编码 |
| `name` | 频道中文名，仅用于可读性与日志 |
| `type` | 该频道的公告类型，取值必须是 `tender`/`win`/`change`/`explore` 之一 |
| `pageCount` | 抓取的列表页数（默认 1，即只抓第一页） |

**`config` JSON 字段语义**：

| 键 | 含义 | 是否必填 |
|---|---|---|
| `baseUrl` | 站点根地址，用于拼接详情 URL | 是 |
| `initialUrl` | **预热访问地址**，先访问它拿到 Cookie 再抓列表/详情（否则 403/限流） | 是 |
| `userAgent` | 浏览器 UA，反爬伪装 | 是 |
| `xhrReferer` | XHR 请求的 `Referer`，仅接口型源站（ztb_gz）需要 | 否 |

**种子数据（2 行）**：

| id | name | code | enabled | interval_ms |
|---|---|---|---|---|
| 1 | 中国政府采购网 | `ccgp` | `b'1'` | 3000 |
| 2 | 贵州省招标投标公共服务平台 | `ztb_gz` | `b'1'` | 3000 |

对应的 `channels` 与 `config` 原文见 [`06-数据采集设计.md`](../技术/06-数据采集设计.md) §三。

### 2.3 `crawler_task` —— 采集任务日志表

> DDL 位置：`backend/sql/mysql/notice.sql` 第 98-120 行
> DO 映射：`tender-module-crawler/.../dal/dataobject/CrawlerTaskDO.java`

**表说明**：每次采集（无论手动触发还是定时触发）为每个站点生成一条记录，贯穿任务的整个生命周期：创建时写入 `start_time` 与 `status = RUNNING`，结束时回填 `end_time`、终态与全部计数器。管理端「数据采集中心」页面消费此表。

| 字段名 | 类型 | 允许空 | 默认值 | 注释 |
|---|---|---|---|---|
| `id` | bigint | 否 | AUTO_INCREMENT | 任务编号 |
| `site_code` | varchar(32) | 否 | — | 站点标识（对应 `crawler_site.code`） |
| `start_time` | datetime | 否 | — | 开始时间 |
| `end_time` | datetime | 是 | NULL | 结束时间 |
| `status` | varchar(16) | 否 | `'RUNNING'` | `RUNNING` / `SUCCESS` / `FAILED` |
| `list_fetched` | int | 否 | 0 | 列表页抓取数 |
| `list_parsed` | int | 否 | 0 | 列表解析出公告数 |
| `detail_fetched` | int | 否 | 0 | 详情页抓取成功数 |
| `detail_failed` | int | 否 | 0 | 详情页抓取失败数 |
| `new_insert` | int | 否 | 0 | 新增入库数 |
| `updated` | int | 否 | 0 | 变更更新数 |
| `error_msg` | varchar(512) | 否 | `''` | 失败原因（代码层截断至 500 字符） |
| 公共字段 | — | — | — | 见 §三 |

**索引**：`PRIMARY (id)`、`KEY idx_site_start (site_code, start_time)` —— 支撑「某站点最近任务」（`ORDER BY start_time DESC LIMIT 1`）与管理端按站点筛选分页。

**状态语义**：

| 状态 | 含义 | 产生时机 |
|---|---|---|
| `RUNNING` | 执行中 | 任务创建时 |
| `SUCCESS` | 成功 | 采完正常结束 |
| `FAILED` | 失败 | 适配器抛异常，或超时被回收（`failStaleTasks(Duration.ofHours(4))`，`error_msg` 为「超时自动回收」） |

> 该表同时承担**防重入**职责：`selectRunningCount(siteCode)` 查出该站点是否有 `RUNNING` 任务，有则跳过本次采集。

### 2.4 `bid_project` —— 投标项目表

> DDL 位置：`backend/sql/mysql/notice.sql` 第 126-149 行
> DO 映射：`tender-module-bid/.../dal/dataobject/BidProjectDO.java`

**表说明**：用户投标闭环的载体。注意 —— 平台定位是**投标管理工具**，真实递交到公共资源交易平台需 CA 数字证书，属线下动作；此表以「报名 → 递交文件 → 开标 → 中标/未中标」的状态机模拟流程。

| 字段名 | 类型 | 允许空 | 默认值 | 注释 |
|---|---|---|---|---|
| `id` | bigint | 否 | AUTO_INCREMENT | 投标项目编号 |
| `user_id` | bigint | 否 | — | 发起用户（**演示默认 1，正式接会员**） |
| `notice_id` | bigint | 否 | — | 源公告编号（逻辑关联 `notice.id`） |
| `project_name` | varchar(512) | 否 | — | 项目名称（冗余自公告，避免详情页回查） |
| `deadline` | datetime | 是 | NULL | 投标截止时间（冗余自公告） |
| `bid_amount` | decimal(18,2) | 是 | NULL | 拟投标金额（万元） |
| `bid_file_name` | varchar(256) | 否 | `''` | 投标文件名（演示为文本，未接对象存储） |
| `status` | varchar(24) | 否 | `'SUBMITTED'` | `SUBMITTED` 已递交 / `OTB` 待开标 / `WON` 中标 / `LOST` 未中标 / `ABANDONED` 放弃 |
| `remark` | varchar(512) | 否 | `''` | 备注 |
| 公共字段 | — | — | — | 见 §三 |

**索引**：`PRIMARY (id)`、`KEY idx_user (user_id)`（我的投标列表）、`KEY idx_notice (notice_id)`（公告关联查询）。

**状态机**：

```
                 ┌──────────────► ABANDONED  放弃（终态）
                 │                    ▲
  SUBMITTED ─────┤                    │
   已递交        │                    │
                 └──► OTB ────────────┤
                      待开标           │
                       ├──► WON  中标（终态）
                       └──► LOST 未中标（终态）
```

| 当前状态 | 允许迁移到 | 触发动作（用户端按钮） |
|---|---|---|
| `SUBMITTED` | `OTB`、`ABANDONED` | 标记开标 / 放弃 |
| `OTB` | `WON`、`LOST`、`ABANDONED` | 确认中标 / 确认未中标 / 放弃 |
| `WON` / `LOST` / `ABANDONED` | —— | 终态，不可再变更 |

**约束**：非法迁移返回错误码 `BID_PROJECT_STATUS_ILLEGAL`；同一用户对同一公告**不可重复在途投标**（判据 `status IN ('SUBMITTED','OTB')`，冲突返回 `BID_PROJECT_ALREADY_EXISTS`）。

> ⚠️ `user_id` 当前取的是**演示值**：`admin` 侧接口由查询参数传入（便于联调），`app` 侧接口从会员令牌取。演示种子数据对应 `member_user.id = 1`（`demo123`）。

### 2.5 `member_user` —— 会员用户表

> DDL 位置：`backend/sql/mysql/tender.sql` 第 1004-1025 行
> DO 映射：`tender-module-member/.../dal/dataobject/MemberUserDO.java`

**表说明**：用户端（`user-web`）的账号表，**与后台管理账号 `system_users` 完全隔离** —— 两套账号体系各自登录、各自发令牌（`UserTypeEnum.MEMBER` vs 后台用户），互不可见、互不可登。这是刻意的设计：门户用户不应出现在后台用户管理里。

| 字段名 | 类型 | 允许空 | 默认值 | 注释 |
|---|---|---|---|---|
| `id` | bigint | 否 | AUTO_INCREMENT | 会员编号 |
| `username` | varchar(30) | 否 | — | 账号（登录名） |
| `password` | varchar(100) | 否 | `''` | 密码（**BCrypt 哈希**） |
| `nickname` | varchar(30) | 是 | NULL | 昵称（注册时默认取用户名） |
| `mobile` | varchar(11) | 是 | NULL | 手机号码 |
| `avatar` | varchar(512) | 是 | `''` | 头像地址 |
| `status` | tinyint | 否 | 0 | 帐号状态（**0 正常，1 停用** —— 注意与框架其他表的习惯相反） |
| `login_ip` | varchar(50) | 是 | `''` | 最后登录 IP |
| `login_date` | datetime | 是 | NULL | 最后登录时间 |
| `creator` / `create_time` / `updater` / `update_time` / `deleted` | — | — | — | 公共字段（**无 `tenant_id`**） |

**索引**：`PRIMARY (id)`、`INDEX idx_username (username)`。

**种子数据**：1 条 —— `id=1`、用户名 `demo123`、密码 `123456`（BCrypt 存储）、昵称「演示会员」、手机号 `13800001111`。与 `bid_project` 中 `user_id = 1` 的演示投标数据对应。

> 注意：该表**没有 `tenant_id` 列**（会员体系不参与租户维度），而业务表 `notice`/`crawler_site`/`crawler_task`/`bid_project` 都有 `tenant_id` 且恒为 0（单租户模式下不使用）。

## 三、公共字段约定（BaseDO）

除 `member_user` 外的业务表均继承框架的 `BaseDO`，携带以下公共列：

| 字段名 | 类型 | 默认值 | 含义 |
|---|---|---|---|
| `creator` | varchar(64) | `''` | 创建者 |
| `create_time` | datetime | `CURRENT_TIMESTAMP` | 创建时间（由框架自动填充） |
| `updater` | varchar(64) | `''` | 更新者 |
| `update_time` | datetime | `CURRENT_TIMESTAMP ON UPDATE` | 更新时间（由框架自动填充） |
| `deleted` | bit(1) | `b'0'` | **逻辑删除标记**。MyBatis-Plus 全局配置：删除值 1、未删除值 0 —— 查询自动追加 `deleted = 0` |
| `tenant_id` | bigint | `0` | 租户编号。当前 `tender.tenant.enable = false`，**单租户模式下恒为 0**，不参与查询条件 |

相关框架配置（`application.yaml`）：

```yaml
mybatis-plus:
  global-config:
    db-config:
      id-type: NONE          # 主键由 DB AUTO_INCREMENT 生成
      logic-delete-value: 1
      logic-not-delete-value: 0
  configuration:
    map-underscore-to-camel-case: true   # 下划线列名 ↔ 驼峰属性名自动映射
```

> `map-underscore-to-camel-case: true` 意味着 DO 里的 `sourceUrl` 属性会自动对应 `source_url` 列，无需 `@TableField` 注解。

## 四、索引总览

| 表 | 主键 | 唯一键 | 普通索引 |
|---|---|---|---|
| `notice` | `id` | `uk_source_url (source_url)` | `idx_type_publish (type, publish_time)`、`idx_province`、`idx_industry`、`idx_publish_time` |
| `crawler_site` | `id` | `uk_code (code)` | —— |
| `crawler_task` | `id` | —— | `idx_site_start (site_code, start_time)` |
| `bid_project` | `id` | —— | `idx_user (user_id)`、`idx_notice (notice_id)` |
| `member_user` | `id` | —— | `idx_username (username)` |

**尚缺的索引**（按预期查询模式，后续数据量上来后需要补）：

- `notice.province + industry` 联合索引 —— 列表页常见的「地区 + 行业」组合筛选目前只能走单列索引。
- `notice.title` 全文索引 —— 关键词检索当前是 `LIKE '%keyword%'`（见 `NoticePortalMapper.selectPage`），**无法走索引**，数据量上万后会明显变慢。规划数据模型中的 `FULLTEXT ... WITH PARSER ngram` 方案可参考 [`08-数据模型-规划.md`](08-数据模型-规划.md)。
- `bid_project.user_id + status` 联合索引 —— 「我的投标」按状态筛选。

| 枚举 | 归属 | 取值 | 代码载体 |
|---|---|---|---|
| 公告类型 `type` | `notice` | `tender` 招标 / `win` 中标 / `change` 变更 / `explore` 采购 | `NoticeTypeEnum` |
| 采集任务状态 | `crawler_task.status` | `RUNNING` / `SUCCESS` / `FAILED` | `CrawlerTaskStatusEnum` |
| 投标状态 | `bid_project.status` | `SUBMITTED` / `OTB` / `WON` / `LOST` / `ABANDONED` | `BidProjectStatusEnum` |
| 会员状态 | `member_user.status` | `0` 正常 / `1` 停用 | —— |
| 站点启用 | `crawler_site.enabled` | `b'1'` 启用 / `b'0'` 停用 | —— |

> 行业取值来自 `NoticeRegionExtractor.INDUSTRY_KEYWORDS` 的 15 个词典项 + 兜底「其他」；省份取值来自其 31 项 `PROVINCES` 数组。两者目前都是**代码内常量**，未落字典表，管理端无法维护。

## 六、与规划数据模型的差异

`doc/` 中另有一份来自产品调研的**规划数据模型**（15 张表，见 [`08-数据模型-规划.md`](08-数据模型-规划.md)），其设计目标是支撑订阅推送、企业画像、竞品分析、监控预警等尚未实现的能力。两者的关系：

| 规划表 | 现状对应 | 落地建议 |
|---|---|---|
| `bid_info`（标讯信息表） | **`notice` 已覆盖核心字段** | 后续按需 `ALTER` 扩展（附件标记、浏览量、更细的子类型） |
| `enterprise`（企业表） | **无** | 二期新建。可从 `notice.tender_person`/`agency`/中标公告正文中抽取企业名 |
| `contract`（合同表） | 无 | 三期，依赖 `enterprise` |
| `contact`（项目联系人表） | `notice.contact`/`contact_phone` 仅单条冗余 | 二期独立成表，一家企业多联系人 |
| `subscription`（用户订阅表） | 无 | **优先级最高**的二期表，订阅推送的前置 |
| `monitor` / `monitor_group` / `monitor_dynamic` | 无 | 三期，依赖 `enterprise` |
| `favorite`（用户关注） | 无 | 二期，成本低收益高 |
| `browse_history`（浏览历史） | 无 | 二期，可与 `favorite` 同期 |
| `bid_attachment`（标讯附件表） | 无（`notice` 未落附件） | 二期，需先实现附件抓取 |
| `project_progress`（项目进度） | 无 | 三期，依赖多类公告的关联匹配 |
| `enterprise_analysis`（企业分析数据） | 无 | 三期，依赖 `enterprise` |
| `crawl_log`（采集日志表） | **`crawler_task` 已覆盖且更细** | 无需新建，沿用现有表 |
| `user`（用户表） | **`member_user` 已覆盖** | 无需新建；会员等级字段可在二期 `ALTER` 加入 |

## 七、种子数据说明

| 表 | 种子内容 | 用途 |
|---|---|---|
| `notice` | 20 条演示公告（id 1-20），四类齐全，含 HTML 正文 | 开发联调、前端演示；正式数据由采集写入 |
| `crawler_site` | 2 行站点配置（`ccgp`、`ztb_gz`） | 采集系统的初始可用配置 |
| `member_user` | 1 条演示会员（`demo123` / `123456`） | 用户端登录联调 |
| `bid_project` | 无种子，由用户操作产生 | —— |
| `crawler_task` | 无种子，由采集产生 | —— |

> ⚠️ 演示账号 `demo123` / `123456` 与后台 `admin` 账号均为**开发用弱口令**，上线前必须更换或删除。
