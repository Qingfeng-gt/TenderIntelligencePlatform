## 项目概览

### 这是什么项目

**招投标情报平台**——从政府法定公开平台采集招标 / 中标公告，归一、去重、结构化入库，让中小企业与个人投标人**直接搜索关键词就能全网查看标讯、寻找商机**，并围绕标讯管理自己的投标。

| 项 | 说明 |
|---|---|
| 对标产品 | 标标达、千里马招标网、剑鱼标讯、立达标讯 |
| 一句话链路 | 源站 → 适配器采集 → `notice` 表去重入库 → 用户端检索浏览 → 发起投标 → 状态流转 |
| 解决的痛点 | ① 公告散落在全国数千个站点，**人工找站难** ② 站点结构各异，爬虫适配成本高 ③ 传统 LIKE 检索召回差，口语化描述搜不到 ④ 标签扁平，无法多维拓扑筛选 |
| 技术形态 | Spring Boot 3.5 多模块后端 + 2 个 Vue3 前端（`user-web` 门户 / `admin-web` 后台）+ `tender-app`（UniApp，本轮新增） |

### 现在做到哪了（毕设的起点）

**一期已交付**：采集（`ccgp` / `ggzy` 两站在运行）+ 检索 + 投标闭环。

| 家底 | 内容 |
|---|---|
| 业务模块 | `tender-module-{crawler,notice,bid,member}`（`system`/`infra` 是芋道脚手架底座） |
| 业务表 | `notice`、`notice_attachment`、`crawler_site`、`crawler_task`、`bid_project`、`member_user`（完整 DDL 见 [`../数据/07-数据模型-现状.md`](../数据/07-数据模型-现状.md)） |
| 前端 | `user-web` 6 个页面、`admin-web`（菜单驱动） |
| 采集 | 已接入 `ccgp`（中国政府采购网）、`ggzy`（全国公共资源交易）——`ztb_gz` 源站已下线停用 |

### 毕设要新增什么

| 工作块 | 新增内容 | 从哪开始 |
|---|---|---|
| M1 | 站点发现 Agent（LLM 判站 + 人工审核） | 0 存量 |

**技术栈**：Spring Boot 3.5 + Spring Security + MyBatis-Plus ｜ MySQL 8 + Redis ｜ Vue3 + Vite + Element Plus + echarts ｜ UniApp ｜ LLM 走 OpenAI 兼容接口（统一走队长的 `tender-spring-boot-starter-ai`）。

## §0 开工前必读：9 处「想当然 vs 真实代码」不一致

> **【工程口径】** 论文规划写于代码成型之前，表名、字段、接口有多处是**设想值**。
> 照着写代码会写出连不上的接口、建不存在的字段、改到别人的表。

| # | 想当然是 | 代码里实际是 | 影响谁 | 处理办法 |
|---|---|---|---|---|
| 1 | 公告主表 `tender_notice` | **`notice`**，另有 **`notice_attachment`** | 乙丙丁戊 | 论文里可叫「公告主表」，**代码里必须写 `notice`** |
| 2 | `crawler_site` 有 `province`/`city`/`site_type`/`adapter_key`/`health_status`/`discovered_by` | 只有 `name`/`code`/`enabled`/`channels`(JSON)/`interval_ms`/`config`(JSON)。**频道不是独立列**，是 `channels` 里的 JSON 数组 | 甲（加列）、乙（读 `channels`/`config`） | 甲按 §4.1 流程加列；乙同步知情——`SourceAdapter` 靠 `channels` 定位栏目 |
| 3 | 爬虫接口 `/admin-api/crawler/task/trigger`、`/crawler/log` | **`/admin-api/crawler/run?siteCode=`**、`/crawler/site/list`、`/crawler/task/page`、`/crawler/task/latest?siteCode=` | 甲乙 | 新增接口按现有 REST 风格命名 |
| 4 | 公告接口 `/app-api/notice/page`、收藏 `/app-api/favorite/toggle` | **`/notice/list`、`/notice/get`、`/notice/stats`**，且**挂在 `/admin-api/notice/**` 下靠放行免登录**；**收藏功能不存在** | 丙丁戊 | 检索扩展做在 `/notice/list` 上；收藏要么丙补，要么从演示砍掉 |
| 5 | 没有投标闭环 | 已有 `/app-api/bid-project/create\|list\|get\|status` + `bid_project` 表（完整状态机） | 丙 | 这是 M3 的**存量资产**，论文里必须写进去 |
| 6 | 已接入 `ccgp`/`ggzy`/`ztb_gz` 三站 | **`ztb_gz` 源站已下线、已停用**（源码保留，一条 UPDATE 可恢复） | 乙 | 只能作为「站点失效与应对」写，不能当运行中站点；实验基线要能换站重跑 |
| 7 | 五模块 = 五个 Maven 模块 | 实际只有 `tender-module-{crawler,notice,bid,member}`；**`-ai`、`-tag`、`-discovery` 均不存在** | 甲丁戊 | 新建模块要改 `backend/pom.xml` 与 `backend/tender-server/pom.xml`——**只有队长能改** |
| 8 | M1 的 Agent 有自己的表 | **`discovery_*` 表不存在** | 甲 | 需新建任务表与候选表 |
| 9 | admin-web 路由前端写死即可 | admin 是**菜单驱动**：`system_menu` 表 + `routerHelper.ts` 的 `import.meta.glob('../views/**/*.{vue,tsx}')`。现有 `/crawler` 菜单是 `notice.sql` 里 id=12800 的一条 INSERT | 甲乙丁戊 | **每加一个 admin 页面必须配一条菜单 SQL**，`component` 要匹配到 `views/` 真实路径 |

## §4 表、DDL 与菜单 id

### 4.1 DDL 文件与执行顺序

现状：`backend/sql/mysql/` 下 `notice.sql` 是**已合并的**产物（原 `notice.sql` + `demo-crawler-bid.sql` + `-seed` + `-admin` 四合一），既有业务表也有菜单种子。
**新约定**：各人新增**自己的** DDL 文件，谁也别改别人的。

**执行顺序**：`quartz.sql` → `tender.sql` → `notice.sql` → `discovery.sql` → `crawler.sql` → `ai.sql` → `tag.sql`
（后四者只依赖 `notice.sql` 建好的表，彼此无依赖）。队长在 [`../运维/11-SQL脚本说明.md`](../运维/11-SQL脚本说明.md) 登记。

**加列流程（3 步）**：① 需要加列的人在自己 sql 文件里写 `ALTER TABLE`（用 `IF NOT EXISTS` 风格或先查 `information_schema`）② 发到群里，**表的主人有 24 小时否决权** ③ 队长合并进运行手册。

### 4.2 BaseDO 约定（新表必须遵守）

每张新表都要有：`creator`、`create_time`、`updater`、`update_time`、`deleted`(bit(1))、`tenant_id`(bigint NOT NULL DEFAULT 0)。
字段注释用中文，风格抄 `crawler_site`。主键 `bigint AUTO_INCREMENT`，种子 id 从 100 起。

### 4.3 `system_menu` 菜单 id 分段（防撞车）

现有 id **12800** = `/crawler`「数据采集中心」（`notice.sql` 第 242 行）。新增菜单按段领用，**不要用邻居的号**：

| 段 | 归属 | 菜单 |
|---|---|---|

## §8 硬性纪律速查

### 8.1 总原则

> ### 子项目相对主项目基线的 `git diff`，必须 100% 落在自己的私有区（§3.2）。
> 公共区（§3.1）出现**任何一行**改动 = 违规。

```bash
# 在子项目根目录执行
git fetch origin main
git diff --stat FETCH_HEAD     # 清单里不允许出现 §3.1 的任何一个文件
```

队长提供 `backend/script/shell/check-subproject.sh <模块名>` 自动判定；**提交前必跑**，CI 上也可以挂。

> **为什么这是总原则**：合并的实质是「把 6 份 diff 叠回主项目」。diff 干净时合并退化成**复制目录**（分钟级）；散落到公共文件就变成**逐行人工仲裁**（天级），而且 6 份会互相踩。

### 8.2 坐标与命名冻结

**合并时最贵的错误是命名不一致**——包名、artifactId、路径只要有一个对不上，就要全局重构。

| 项 | 冻结值 | 不一致的后果 |
|---|---|---|
| Maven `groupId` | `com.tenderintelligence` | 需全局改包 |
| 模块 `artifactId` | `tender-module-{discovery,crawler,notice,ai,tag}` | 同上 |
| Java 包根 | `com.tenderintelligence.module.{...}` | 同上 |
| 接口前缀 | 管理端 `/admin-api/**`、会员端 `/app-api/**` | 决定鉴权链。**踩过的坑：会员 token 打 `/admin-api` 必定 403** |
| admin 页面路径 | `admin-web/src/views/{模块}/{页面}/index.vue` | 菜单 `component` 靠 `import.meta.glob` 匹配，错了表现为**点开是空白页**（不报错，极难排查） |
| **App 工程路径** | **`tender-app/`**（顶层，与 `admin-web/`、`user-web/`、`backend/` 平级） | 合并时无法按名归位；**不许塞进 `user-web/`**——它是独立工程 |
| DDL 文件名 | `{discovery,crawler,ai,tag}.sql` | 合并时无法按名归位 |
| 新建表名 | 带模块前缀：`discovery_*`、`ai_*`、`tag_*` | 新表撞名 |
| App 调用的接口 | 公告走 `/admin-api/notice/*`、投标走 `/app-api/bid-project/*` | 公告接口**挂在 admin 前缀下**（靠放行免登录）是本项目的历史怪癖 |

### 8.3 依赖冻结

**规则**：子项目**不许引入 `tender-dependencies` BOM 之外的依赖**。

1. 必须引入时，填申请表：**坐标 + 版本 + 用途 + 谁会用到**
2. **允许**在自己模块 `pom.xml` 里先写死版本（自己的私有区，不违规）
3. **合并时由队长统一上提到 BOM**（毕设规模下依赖有限，手工上提几分钟）
4. **禁止**引入会波及全平台的传递依赖升级（Jackson / Guava / OkHttp / Spring 系）——版本打架会让 6 个模块同时炸

### 8.4 数据库硬规范

1. **只许建自己名下的表**。改别人表的列 → 禁止；确实要改走「加列申请」（§4.1），**表主人有 24 小时否决权**。
2. **新表必须带 BaseDO 六件套**（§4.2）。虽然 `tenant.enable=false`，但 `tenant_id` 列**必须保留**，否则框架自动填充报错。
3. **字段注释用中文**，风格抄 `crawler_site`；主键 `bigint AUTO_INCREMENT`，种子 id 从 100 起，按段分配防撞。
4. **DDL 文件可重复执行**：沿用 `notice.sql` 风格（`DROP TABLE IF EXISTS` + `CREATE TABLE`）。
5. **禁止**在子项目里改 `tender.sql` / `quartz.sql`。

### 8.5 前端硬规范

1. **admin 新增页面不用改路由**（菜单驱动），但**必须配 `system_menu` 记录**，`component` 写 `views/` 相对路径。菜单 id 已在插槽 3 预置，**别自己插**。
2. **user 新增页面**：占位页 + 路由 + 导航已由插槽 4 预置，**替换占位页内容即可**。
3. **不许引入新的前端框架/UI 库**。只用 **Vue3 + Element Plus + echarts**；要加别的可视化库走申请表（§8.3）。
4. 样式一律 **`scoped`**，禁止全局选择器污染——5 个人的样式合并后互相覆盖，是前端最隐蔽的坑。
5. **禁止**改 `admin-web/src/{store,router,utils,components,hooks,layouts}`、`user-web/src/{layouts,components,utils}`。

### 8.6 配置与密钥硬规范

1. **不许改 `application*.yaml` 的既有行**。自己的配置写进插槽 6 预置的 `tender.{模块}:` 段，用 `@ConfigurationProperties(prefix = "tender.xxx")` 读。
2. ⚠️ **API key 一律不许写进 yaml**。`application-local.yaml` 与 `application-dev.yaml` **已被 git 跟踪**，写进去就是提交进仓库。
   正确写法：`api-key: ${DEEPSEEK_API_KEY:}`，密钥走环境变量或本地未跟踪文件。
3. 本机调试可以改 `application-local.yaml` 的数据库/LLM 地址，**但合并前必须还原**（这也是它算公共区的原因）。

### 8.7 每周同步

**每周一次**把子项目基线更新到主项目最新（**别攒到第 7 周**）：

```bash
git fetch origin main
git rebase FETCH_HEAD        # 冲突当场解决
```

> 攒 7 周的 diff 是合并灾难：主项目改一次公共文件，6 个子项目的 diff 全部失效。每周同步 = 每次冲突只有几行。

### 8.8 一页速查（贴给队友）

| 我要… | 怎么做 |
|---|---|
| 加一张新表 | 建到自己模块的 sql 文件里，带 BaseDO 六件套 |
| 改别人表的字段 | 不许直接改，走加列申请（§4.1） |
| 加一个后端接口 | 前缀选对：管理端 `/admin-api`、会员端 `/app-api` |
| 加一个 admin 页面 | 放进 `views/{模块}/`，**不用改路由**，菜单已预置 |
| 加一个 user 页面 | 替换已预置的占位页，**不用改路由** |

| **App 要登录（甲）** | 验证码开关已由队长在插槽阶段关掉，**你不用碰 yaml** |

## §9 分发与合并协议

### 9.1 冻结与合并顺序

6 个子项目各自打 tag：`m1-v1.0` ~ `m6-v1.0`。冻结后不再接受新提交。

**顺序有依赖，不能乱**：

```
1. 丙 (notice/bid/member + NoticeApi 实现)   ← 乙/丁/戊 依赖它的实现
2. 乙 (crawler)                              ← 已依赖 tender-module-notice
3. 甲 (discovery)                            ← 无依赖，位置随意
4. 丁 (ai)                                   ← 依赖 NoticeApi
5. 戊 (tag)                                  ← 依赖 NoticeApi
6. 甲 (tender-app)                           ← 零后端依赖，放最后最安全
```

> 甲占两个位置（M1 与 M6），**两者互相独立**，可分开合并、分开验证。

### 9.2 每个子项目的合并动作

只抽这几类东西，**逐类归位**：

| 抽取 | 落到主项目 |
|---|---|
| `backend/tender-module-{x}/` 整个目录 | 同名目录（覆盖空壳模块） |
| `backend/sql/mysql/{x}.sql` | 同名新文件 |
| `admin-web/src/{views,api}/{x}/` | 同名目录 |
| `user-web/src/{views,api}/...` 新增或替换的**自己的**文件 | 同名文件 |
| **`tender-app/`** 整个目录 | 同名顶层目录（最干净的一类——**整目录替换，零归位判断**） |
| `doc/毕设/` 自己那节 | 手工并 |

**合并不做的事**：不 cherry-pick 子项目的公共区改动——按规范那里**本来就不该有任何改动**。若检查后确实动了公共区，逐条判断「必要的」还是「违规的」，必要的手工搬。

### 9.3 合并后验证（四项）

```bash
cd backend && mvn clean package -DskipTests     # ① 后端全模块编译
cd admin-web && npm run build && cd ../user-web && npm run build   # ② 两个 Web 前端
cd ../tender-app && npm install && npm run build:h5                # ③ App 工程能构建
# ④ 按 §4.1 顺序全量重建数据库，确认 DDL 无冲突
```

> ⚠️ 构建验证**必须在 Linux 侧（或 WSL）也跑一次**。本仓库踩过这个坑：**Windows 大小写不敏感 + `core.ignorecase` 会隐藏纯改名**，本地构建正常但 Linux CI 报 `UNLOADABLE_DEPENDENCY`。多人并行加文件后出现概率大增。

## §11 队长职责与模块认领

### 11.1 串联（工程集成）

1. **底座与模块注册**：`backend/pom.xml`、`tender-server/pom.xml`、`application.yaml`——**只有队长改**。
2. **菜单 SQL 合并**：各人交菜单 SQL，队长统一合并执行，避免 id 撞车与重复菜单。
3. **契约仲裁**：接口有争议时拍板，并更新 §5 契约表。
4. **DDL 合并与执行顺序**：维护 [`../运维/11-SQL脚本说明.md`](../运维/11-SQL脚本说明.md)。
5. **CI 看护**：`.github/workflows` 已有前后端构建，**本轮要加第三路——`tender-app` 的 uni-app 构建**。注意大小写那个坑（§9.3）。
6. **集成测试与演示数据**：维护一份全组共用的演示数据集（500~1000 条真实公告），各人演示都从这里取。
7. **文档看护**：[`../README.md`](../README.md) 索引、各人更新自己负责的章节。
8. **子项目合并**：第 7 周把 6 份 diff 叠回主项目的唯一执行人（§9）。

### 11.2 商业化落地（论文之外的额外工作）

论文做完 ≠ 产品可用。对照 [`../产品/01-产品定位与目标.md`](../产品/01-产品定位与目标.md) 的能力对照表逐项转：

| 论文产物 | 转成什么产品能力 |
|---|---|
| 甲：站点发现 Agent | **站点准入流水线**——决定平台能覆盖多少源站 |
| 乙：爬虫框架 | **数据供给**——日更量是平台的生命线 |
| 丙：架构 + 投标闭环 | **平台可用性 + 付费点**（会员、投标管理） |
| 丁：语义检索 | **最强差异化卖点**——建议放付费墙后 |
| 戊：标签体系 | **留存与转化**——多维筛选是反复回来的理由 |

**要额外补的四件事**：① **合规**（`robots.txt`、请求频率、公告版权边界）② **稳定性**（断点续跑、站点失效自动降级——`ztb_gz` 已演示过一次风险）③ **成本**（甲/丁/戊 三块都烧 token，要算出「每条公告的 LLM 成本」再定免费额度）④ **数据量级**（毕设是 500 条，产品起步要 10 万+）。

### 11.3 队长认领哪个模块 【待确认】

**关键前提**：队长**也是 5 人之一**——不是在 5 个人之外「再认领一块」，而是**在甲/乙/丙/丁/戊 这 5 个身份里选定一个当自己**。
所以「队长认领 M1 让甲卸掉 M1」是**做不到的**：那等于 6 个人。

| 你 = | 你拿到的工作块 | 判断 |
|---|---|---|
| 甲 | M1 工程 **+** M6（3 份同功能实现 + 论文） | ⛔ 全组唯一被登记的风险 ①，再叠加队长职责，必崩 |
| **乙** | M2 爬虫（**4.5k LOC 已存在**） | ✅ **建议** |
| 丙 | M3（3 个模块 + user-web 全部 6 页 + ES/Redis + 压测 + `NoticeApi`） | ⚠️ 原建议，见下方反对理由 |
| 丁 | M4（0 存量 + 200 条人工标注 + 实验最厚） | ⛔ 标注是纯人力活，撞上你的联调一 |
| 戊 | M5（0 存量 + 500 条标注，但最自包含） | 次选 |

**为什么建议乙**

1. **起点优势的边际价值最大**——你时间最少，「已有 4.5k LOC」对你最值钱。全组没有第二块模块有这个存量（丙只有 1.7k 且大多是 CRUD，丁戊是 0）。
2. **不持有枢纽**——M3 是乙/丁/戊 三个模块的交汇点。**队长持有枢纽 = 你一滑三个人全停**，而你的第 1 周已被 8 个插槽 + 分发 6 份副本 + 契约冻结占满。
3. **外部依赖最少**——只依赖丙的 `NoticeApi`（§6 第 6 项）。丁/戊 不依赖你的代码，只依赖数据量。
4. **论文最"实"**——代码已存在，写作更机械。你要同时扛 8 项串联职责 + 商业化落地，需要一篇不需要从零推导的论文。

**为什么原建议（丙）是错的**：原文理由是「M3 是交汇点，队长天天在看这些文件，职责天然合并」。但**看文件和实现是两件事**——仲裁权来自 §5 契约表，不来自「拥有它」。而 M3 的增量是全组最大的（3 个模块 + user-web 全部 + ES/Redis + 压测 + 收藏订阅），把它压在时间最少的人身上，等于让**全组的公共依赖**跟着你一起冒风险。

> 若你的真实情况是「不想写爬虫论文」（比如爬虫代码是接手来的、讲不清设计动机），则**戊优于丙**：它最自包含、没有人在等它。代价是 0 存量 + 500 条标注。
