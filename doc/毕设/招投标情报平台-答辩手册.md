## 2. 乙 —— M2 招投标网站爬虫

| 项 | 内容 |
|---|---|
| **论文题** | 面向多源异构招投标站点的可配置爬虫框架与正文结构化抽取研究 |
| **核心问题** | 招投标站点结构各异、反爬策略多、字段抽取难。如何设计一个框架让新站点快速接入，并稳定抽取结构化字段？ |
| **研究内容** | ① **适配器 SPI 框架**：把"列表页发现 → 详情页抓取 → 正文解析 → 附件下载 → 字段抽取"五步抽成模板方法 ② **反爬对抗策略**：UA 轮换、请求间隔随机化、Cookie 池、对 JS 渲染站点接入 Playwright 兜底 ③ **LLM 辅助正文结构化抽取**：对规则难解析的页面，把 HTML 喂给 LLM 抽取字段，与规则抽取做对比 ④ **增量去重**：`source_url` 唯一键 + 标题 SimHash 二次去重 |
| **创新点** | ① 适配器 SPI 框架 + 规则可视化配置（字段抽取规则存 DB）② **规则抽取与 LLM 抽取双路融合**——规则类字段 100% 确定，难解析字段用 LLM 兜底 |
| **实验设计** | ① **连续 30 天数据采集**：统计日抓取量、成功率、字段抽取准确率 ② **规则 vs LLM 抽取对比**：200 条难解析公告，对比规则 / 纯 LLM / 融合三种方法 ③ **反爬策略效果**：不同频率 / UA 策略下的封禁率<br>**预期**：融合抽取准确率 ≥ 90%，日抓取 ≥ 5000 条 |
| **章节结构** | 1 绪论（招投标数据孤岛、反爬现状）／2 相关技术（Jsoup、OkHttp、Playwright、SimHash、LLM 信息抽取）／3 需求分析（≥3 个站点、日抓取 ≥5000、字段准确率 ≥90%）／4 系统设计（适配器类图、抓取时序、字段抽取规则表、去重算法、反爬策略矩阵）／5 实现（按 ccgp/ggzy/贵州 ztb 三适配器分别讲，重点讲 LLM 抽取兜底）／6 实验与分析／7 总结与展望 |

## 4. 丁 —— M4 大模型语义模糊查找

| 项 | 内容 |
|---|---|
| **论文题** | 基于查询理解与混合检索的招投标公告自然语言搜索方法研究 |
| **核心问题** | 投标人常用口语化描述（"我想找贵阳 50 万以下的弱电项目"），传统数据库 LIKE 召回差。如何让系统理解自然语言并返回相关公告？ |
| **研究内容** | ① **查询理解**：用 LLM 把口语化查询解析成结构化过滤条件（地区/预算上限/语义关键词）+ 纯语义 query ② **混合检索**：向量召回（Embedding 语义）+ BM25（关键词）+ 结构化过滤（地区/金额）三路召回，结果融合 ③ **Rerank 重排序**：用 Rerank 模型或 LLM 对召回结果二次排序 ④ **评测数据集构建**：人工标注 200 条查询的相关公告，作为实验基准 |
| **创新点** | ① LLM 查询理解——把口语化输入拆成"结构化过滤 + 语义 query"双路 ② 三路召回融合（向量 + BM25 + 规则），面向招投标领域的混合检索方案 ③ 构建招投标领域搜索评测数据集（200 条标注），可作为后续研究基准 |
| **实验设计** | **指标**：Recall@10、MRR、NDCG@10<br>**对比方法**：① MySQL LIKE ② 纯向量检索 ③ 纯 BM25 ④ 本文混合检索 ⑤ 混合 + Rerank<br>**额外对比**：不同 Embedding 模型（bge-m3 vs text-embedding-3）<br>**预期**：混合 + Rerank 的 Recall@10 ≥ 0.85，比 LIKE 提升 50%+ |
| **章节结构** | 1 绪论（传统数据库检索在招投标场景的局限）／2 相关技术（Embedding 模型、向量数据库、BM25、Rerank、RAG）／3 需求分析（输入一句自然语言，3 秒内返回 Top20）／4 系统设计（查询理解 Prompt、三路召回融合架构、Rerank 流程、评测指标）／5 实现（`tender-module-ai`）／6 实验与分析（200 条标注查询的对比实验，5 种方法表格 + 折线图）／7 总结与展望 |

## 5. 戊 —— M5 标签拓扑查询系统

| 项 | 内容 |
|---|---|
| **论文题** | 面向招投标公告的领域标签体系构建与共现图谱推理研究 |
| **核心问题** | 扁平标签无法支撑"行业 × 地区 × 金额 × 采购方式"多维筛选，也无法发现标签间的关联。如何构建有层次、可推理的标签体系？ |
| **研究内容** | ① **标签本体设计**：四层标签体系——行业（参考国标行业分类）、地区（行政区划码：省→市→区县）、金额（<50 万 / 50~200 万 / 200~1000 万 / >1000 万）、采购方式（公开招标/邀请招标/竞争性谈判/竞争性磋商/询价/单一来源）② **双路自动打标**：规则打标（金额、地区、采购方式——直接从乙抽取的字段映射）+ LLM 打标（行业标签，带置信度，低于阈值转人工）③ **标签共现图谱**：统计标签 co-occurrence 矩阵，用 Louvain 社区发现算法发现标签簇 ④ **标签推理推荐**：基于共现矩阵，用户选了"弱电智能化"，推荐常共现的"贵阳市/公开招标/<50 万" |
| **创新点** | ① 面向招投标公告的领域标签本体设计（四层、可扩展）② 规则 + LLM 双路打标，规则类 100% 确定、LLM 类带置信度阈值 ③ 基于共现矩阵的标签推理推荐，不是手工配置关联 |
| **实验设计** | ① **打标准确率**：人工标注 500 条公告的行业标签，对比规则 / LLM / 双路融合 ② **标签图谱质量**：共现矩阵社区发现后，人工评估标签簇是否合理 ③ **标签推理推荐效果**：20 个测试场景，看推荐标签的命中率<br>**预期**：双路打标准确率 ≥ 88%，推荐标签命中率 ≥ 70% |
| **章节结构** | 1 绪论（扁平标签的局限、标签体系对检索的价值）／2 相关技术（文本分类、知识图谱、标签本体、社区发现算法 Louvain）／3 需求分析（标签管理、自动打标、拓扑图浏览、多维筛选）／4 系统设计（标签本体 UML、双路打标流程图、共现矩阵计算、标签推理算法）／5 实现（`tender-module-tag`）／6 实验与分析（打标准确率对比、社区发现可视化、推荐命中率）／7 总结与展望 |

# 第二部分 独立答辩演示方案


> **【论文口径】**

### 1 核心原则

1. **自闭环**：打开自己的演示页面 → 用自己模块的数据 → 讲完自己的研究故事，不卡壳；
2. **不依赖他人**：甲不需要等乙的爬虫真跑，乙不需要等甲的站点清单，丁不需要等丙的前台接好；
3. **论文里"系统整体"只是背景**：第 4 章系统设计开头花半页图画个整体架构图，说明"我在哪个位置"，然后立刻切回自己模块的细节；
4. **每个人准备一份"演示数据包"**：预先录好 / mock 好自己模块需要的数据，答辩当天直接用，不现场跑长流程。

**不依赖什么**：不需要丙的 user-web 真的接好——自己做独立 demo 页；不需要乙的爬虫持续抓新公告——预先选 500 条公告跑一遍打标；不需要现场跑 LLM 打标——拓扑图和标签云是预先算好的静态数据。

**演示数据包**：500 条公告预先打好标签；共现矩阵预先算好，echarts 图的数据文件准备好；准备一张"打标准确率对比"表格截图（规则 82% / LLM 85% / 双路融合 91%）。

**答辩话术（1.5 分钟）**

> "扁平标签只能一个一个筛，我设计了一个四层标签体系——行业、地区、金额、采购方式，并且从公告数据里统计标签共现关系，画出标签拓扑图。用户点'弱电智能化'，系统会自动推荐常和它一起出现的'贵阳市''公开招标''50 万以下'这些标签，帮助投标人多维筛选。打标准确率达到 91%。"

### 7 论文里"系统整体"怎么写

答辩不串联，但论文里**第一章绪论**和**第四章系统设计开头**必须交代"我在整个系统中的位置"。

写法模板（每个人都可以套）：

```
第 1 章 绪论
  1.1 研究背景（招投标信息孤岛、传统检索局限）
  1.2 国内外研究现状
  1.3 本文研究内容
      "本团队设计并实现了一个招投标情报平台，
       本文聚焦其中的【自己模块】子系统……"
  1.4 论文组织结构

第 4 章 系统设计
  4.1 系统总体架构（半页图，标出自己模块在哪个位置）
  4.2 【自己模块】需求分析
  4.3 【自己模块】详细设计 ← 后面全是自己的内容
```

**关键**：总体架构图花半页讲清楚就行，**不要花一章写别人的模块**。

# 附录 A ReAct 循环概念解释

> 甲 M1 的技术参考（M1 已降级为仅工程，本文不作为论文主题）。也适用于丁的查询理解设计参考。

## 一句话理解

ReAct = **Re**asoning（推理）+ **Act**ing（行动），是 LLM Agent 最经典的工作范式。核心：**让大模型一边想、一边动手查外部工具，查完再想，循环直到任务完成**。

普通聊天是"你问一句，模型答一句"，模型脑子里没有实时信息。ReAct 是让模型学会：**遇到不知道的事情，先调用工具查一下，再根据查回来的结果继续想**。

## 循环长什么样

```
Thought（思考）：我现在需要什么信息？下一步该干嘛？
Action（行动）：调用某个工具，比如搜一下 / 抓个网页 / 查数据库
Observation（观察）：工具返回的结果是什么？
（回到 Thought，继续想……）
...
直到模型判断信息够了，输出 Final Answer
```

## 用 M1 场景走一遍

任务："帮我发现贵州弱电相关的招投标网站"

```
Thought: 我需要先搜索"贵州 弱电 招标"相关的网站。
Action: 调用 SearchTool("贵州 弱电 招标")
Observation: 返回 10 个 URL，包括
  - ccgp-guizhou.gov.cn（贵州政府采购网）
  - ggzy.guizhou.gov.cn（贵州公共资源交易）
  - zhihu.com/question/123（知乎讨论帖）
  - zhaobiao.xxx.com（某装修公司站）

Thought: 搜索结果里混了知乎和装修公司站，需要逐个判断。
先抓第一个贵州政府采购网首页看看。
Action: 调用 FetchTool("https://ccgp-guizhou.gov.cn")
Observation: 返回首页 HTML，标题含"中国政府采购网贵州分网"，有"招标公告"栏目。

Thought: 这个站看起来是真的政府采购网。再抓第二个公共资源交易站确认。
Action: 调用 FetchTool("https://ggzy.guizhou.gov.cn")
Observation: 返回首页 HTML，标题含"贵州公共资源交易中心"。

Thought: 知乎和装修公司站大概率不是招投标站，但为了确认，抓一下装修公司站。
Action: 调用 FetchTool("https://zhaobiao.xxx.com")
Observation: 首页是"XX装修公司欢迎您"，没有招标公告栏目。

Thought: 信息够了。真正的招投标站是 ccgp-guizhou 和 ggzy-guizhou，
把它们写入候选站点表，给每个站打分。
Final Answer: 发现 2 个有效站点，已写入 crawler_site 表。
```

## 在系统里怎么写

M1 的系统设计可以画这样一张流程图：

```
┌─────────────────────────────────┐
│         用户输入种子关键词        │
└──────────────┬──────────────────┘
               ▼
        ┌─────────────┐
        │  LLM Thought │◄────────────┐
        └──────┬───────┘             │
               ▼                     │
        ┌─────────────┐              │
        │  Action 工具调用            │
        │  Search/Fetch/Judge        │
        └──────┬───────┘              │
               ▼                     │
        ┌─────────────┐              │
        │ Observation │──────────────┘
        │ 工具返回结果 │  （信息不够则回到 Thought）
        └──────┬───────┘
               ▼
        ┌─────────────┐
        │  判断信息够不够？          │
        │  够 → Final Answer         │
        │  不够 → 回到 Thought       │
        └─────────────┘
```

## 工程上怎么实现

不用自己造轮子，Spring AI 或 LangChain4j 都内置了 ReAct 支持。核心就是给 LLM 喂一个 System Prompt：

```
你是一个招投标站点发现助手。你可以使用以下工具：
1. SearchTool(keyword) - 搜索引擎搜索
2. FetchTool(url) - 抓取网页 HTML
3. JudgeSite(html) - 判断是否招投标站

每次回答必须按以下格式：
Thought: 你现在的思考
Action: 工具名(参数)

观察到工具返回后，继续 Thought。
当你认为信息足够时，输出：
Final Answer: 最终结果
```

然后写一个循环：解析模型输出 → 如果是 Action 就调工具 → 把 Observation 拼回 Prompt → 再让模型想 → 直到出现 Final Answer。
